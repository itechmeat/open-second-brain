# Wiring shipped seams - per-session pool cap, usage-ordered skill offers, seeded LongMemEval sampling, and the OpenCode V2 config shape

**Status:** draft
**Author:** feature-release-playbook orchestrator
**Audience:** implementation

## Problem statement

Four verified cards in this wave share one defect family: the last unblocked wiring step on a surface the codebase already ships. The recall pipeline's diversity stage is similarity-based MMR over the ranked pool, so near-duplicate chunks collapse while several distinct chunks of one long imported session can still fill the whole reranker-facing window; the per-turn skill offer is ordered by lexical score alone even though a usage store with invocation counts and decay weights already ships; the bench harness runs every fixture wholesale even though the LongMemEval lane shipped in v1.82.0, so run-to-run score movement conflates retrieval changes with question-mix noise; and the OpenCode install adapter writes only the V1 top-level `mcp` key with a plain JSON round-trip that would strip JSONC comments, while OpenCode V2 hosts read the native `mcp.servers` shape and `.jsonc` config files. Every residue is an extension of a proven in-tree subsystem, verified anchor by anchor by the recon node against this exact worktree.

## Scope

- t_68ae8a53 (lane 4) - the corrected residue: the OpenCode adapter learns the V2 shape - detection by file shape (`mcp.servers` present means the native key), `.jsonc` config path support, comment-preserving token-offset edits through a vendored minimal JSONC editor (the repo has no JSONC dependency; the design decision is explicit below), verify reconstruction kept symmetric with apply, the doctor registered-command probe taught the nested key, V1 installs untouched.
- Integration lane - docs pages (cli-reference, how-it-works, mcp, observability, install/opencode, updating, README plus the plugin mirror sync), CHANGELOG entry, the minor version bump via scripts/sync-version.ts inside this pull request, census reconciliation and the full local gate run.

## Out of scope

- A generic sampler for the locomo or surfacing-replay suites: type-proportional stratification is LongMemEval-only (locomo carries a free-text category hint mapped to the four collapsed BenchCategory values, weaker than the card's ask). The loader options shape leaves room for a later generic cap.
- Explicit operator-tuned stratum proportions: proportional-to-population is the card's ask; a proportions override is a tuning surface nobody has asked to tune.
- A bounded trailing window for `deriveSkillUsage`: the read model already decays weights; windowing changes which records establish the decay baseline and is a semantic change of its own. The knob derives once per attach call only when on; cost is documented.
- Usage ordering for `skills_attach` tool help beyond a one-line mention, and any README skills section (README carries no skills_attach mention today; the triggers knob's docs footprint was docs/mcp.md only).
- A V2 plugins-config-object registration for the bundled plugin: the plugin is a local file installed by file-drop, the V2 config object targets package-name plugins (bare name, version-pinned spec, or options tuple), and directory plugin loading is what V2's removal directives (`-name`, `-glob`) presuppose. The plugin keeps its no-imports rule and spool-only writes.
- Automatic migration of an existing healthy top-level `mcp` entry into `mcp.servers`: V2 hosts keep reading a legacy declaration (upstream's own rule: native declarations win, an existing legacy declaration must not be shadowed), so migration would churn every existing install and trip the user-modified-block guard for zero benefit.
- Preserving an operator's explicit `enabled: false` as non-drift: today an explicit disable is drift by design ("an operator toggling the server off shows up as drift instead of silently staying off after re-apply"); that contract stays, on both shapes, this wave.
- A symlink-safe atomic write (realpathSync before rename): a pre-existing V1-path hole, recorded under risks, not this wave.
- Version bump outside the pull request, new MCP tools (the tool census is pinned), new continuity record kinds, and any new external dependency.

## Chosen approach

Variant 1: four parallel file-disjoint lanes with one bench contract commit first (consultant recommendation, orchestrator agrees; full text of all variants and the decision record in `variants.md`).

Lane 3 (bench sampler) lands its contract commit first - CLI flags, loader options widening, capability declaration - because lane 1 holds the wave's only append-only right on a lane-3 file: the new knob name in `BENCH_PIN_NESTED_KEYS.recall` in src/cli/brain/verbs/bench.ts, exercisable only after that commit. Lanes 1 (per-session pool cap), 2 (skill usage ordering) and 4 (OpenCode V2 adapter) then run concurrently over fully disjoint file sets with no other declared dependency; each lane's pure module is testable in isolation from its first commit. One integrator pass closes census reconciliation, docs, the CHANGELOG entry, the version bump and the full local gate run in CI order.

## Design decisions

1. **t_bb6ce095 - the cap groups by SOURCE import-session identity read through the existing frontmatter cache.** Candidate rows carry no session id, so the cap derives one per row at assemble time: `readCachedFrontmatterEntry` over the `FilterContext` the assemble closure already builds, giving one parsed-frontmatter read per path per search. Group key: a non-empty string `session_ref`, else a non-empty string `session_id` (handoff notes), else null - rows without identity, and rows whose frontmatter is unreadable, pass through uncapped, mirroring the `duplicateKey` null handling. Ordinary vault notes are therefore untouched by construction; in a vault of ordinary notes the knob is a measured no-op, and the docs say so.
2. **t_bb6ce095 - placement and widening: floor, then cap, then diversity.** The cap phase sits after the relevance floor and before `mmrRerank` and `rerankByRelevance` (assemble.ts:330-348), so the diversity pass selects across sessions rather than inside one and the floor never wastes cap slots on rows it would drop. When the cap is active (value > 0), it joins the existing `Math.max` pool-width composition by extending the widening disjunction (assemble.ts:249-257) - a wider pool is required or the cap merely truncates sooner. The backfill trigger is deliberately NOT extended: the cap adds no trigger condition of its own. Reviewed against the shipped pipeline, for plain queries the backfill's `wideCap` (`Math.max(limit * 5, 50)`, semantic-phase.ts:59-61) exceeds the cap-widened `rankLimit` (`Math.max(limit, limit * 3, 30, topK)`; `semanticPoolSize` joins only through `baseRankLimit`, which plain queries do not use), so a backfill that fires for its own pre-existing reasons (visibility drops, merges leaving an under-filled window) re-runs with the cap active over the wider pool: the cap is re-applied in the second pass, the window can only grow, and `noteAssemblyNarrowings` reports the final pass. Folding `semanticPoolSize(limit)` into the widened composition to keep the cap single-pass would change the backfill's width for every query - a behavior change beyond this wave's mandate - so the honest contract is: the cap never adds a retry reason, and a pre-existing backfill re-runs the cap. (Review revision, pr-251 M2-M4/L4: the cap now groups frontmatter-less rows by path and runs AFTER the caller's filters - which moves it past the diversity rerank, so "floor, then cap, then diversity" above no longer holds and the caller's scopes can never be starved by cap slots spent on rows they would drop - and the backfill trigger now DOES include the cap's own under-filled drops, with one re-widen at `limit * (widestGroup + 1)`; a value at or above the query's resolved pool width is treated as off, the fingerprint still folding.)
3. **t_bb6ce095 - the knob rides the search_mmr_lambda plumbing exactly.** `search_pool_max_per_session` / `OPEN_SECOND_BRAIN_SEARCH_POOL_MAX_PER_SESSION`, integer, default 0 (off), parsed in `resolveSearchConfig` beside the mmrLambda parse, validated in `validateResolvedConfig`, surfaced as an OPTIONAL `ResolvedRecallConfig.poolMaxPerSession` field spread-omitted when 0 (the `relationalRerankPin` pattern at index.ts:1175-1178, so exact-shape assertions on the resolved config keep holding), with a per-query `SearchOptions.poolMaxPerSession` override following the mmrLambda pattern. Results-affecting folds are mandatory: `configFingerprint` gains the resolved value (cache-slot.ts) and the per-query cache key gains the override (query-cache.ts) - a knob missing from either serves stale cached rows. `BENCH_PIN_NESTED_KEYS.recall` gains the knob name or a `--pin '{"recall":{...}}'` naming it is refused. Off means the phase never runs and no frontmatter reads are added: byte-identical, and free.
4. **t_bb6ce095 - drops are named, once.** A new `RETRIEVAL_DEGRADATION` code `source-session-capped-rows` (detail.dropped, detail.cap) joins retrieval-trail.ts beside `relevance-floor-dropped-rows`, noted once in `noteAssemblyNarrowings` - the name says SOURCE session so the degradation trail never conflates the cap with the caller's session focus. The assemble closure can run twice only via the backfill; the cap never adds a trigger (decision 2), and `noteAssemblyNarrowings` is called once per answer on the final assembly, so the note stays once per answer even when a pre-existing backfill re-runs the cap.
5. **t_5d1ec8a8 - one ranking point, a multiplicative composite, lexical scores preserved as primary.** `BuildSkillAttachmentOptions` gains `usageWeight?: ReadonlyMap<string, number>` (skill name to decay weight); the map is absent when the knob is off, so both `buildSkillAttachment` and the decision-model shortlist inherit the input unchanged through `DecisionSkillAttachmentOptions`. Inside `rankSkillCandidates`, after the discriminating-term floor and before the slice, when a usage map is present the order becomes the composite `score * (1 + SKILL_USAGE_ORDERING_MAX_BOOST * weight)` descending, then name ascending - with `SKILL_USAGE_ORDERING_MAX_BOOST = 0.5` a named module constant and weight the `SkillUsage.weight` decay value in (0, 1]. A maximally-used skill earns at most +50 percent on its lexical score, so usage can lift a daily skill over a slightly hotter one-off but can never rescue a non-matching skill past the floor. The returned `score` field stays the lexical score; the OFF path returns the scorer's order untouched (byte-identical). The documented invariants at skill-attach.ts lines 4-8 and 126 are amended in the same commit to state the gated contract: absent usage input, ranking stays the scorer's.
6. **t_5d1ec8a8 - the flag rides the skills_attach_triggers plumbing exactly.** `skills_attach_usage_ordering` / `OPEN_SECOND_BRAIN_SKILLS_ATTACH_USAGE_ORDERING`, default off, via `resolveConfigFlag` beside the other skill gates in src/core/config.ts, resolved once in `toolSkillsAttach` and passed to both build paths. When on, the tool layer derives usage exactly once per attach call with an explicit `nowMs: Date.now()` (one clock read per call; `decayWeight` itself is pure, tests pin nowMs as skill-usage.test.ts already does), and builds the map through a new pure helper in src/core/brain/skill-usage.ts so the continuity reader set is unchanged (reader-census stays green).
7. **t_5d1ec8a8 - the type is a local structural input, not a cross-layer import.** skill-attach.ts declares the map shape locally (`ReadonlyMap<string, number>`); core/surface never imports core/brain. The repo's import-cycle ratchet counts `import type` as an edge, and core/brain/skill-usage.ts already imports from core/surface - the reverse edge would close a cycle.
8. **t_5d1ec8a8 - plugin-qualified invocation names are normalized at map-build time, never by rewriting records.** The Claude Code `Skill` tool stores `payload["skill"]` exactly as invoked (`open-second-brain:codegraph-partner`), which never equals the discovered bare name. The new `skillUsageWeights(usage, knownNames)` helper joins by exact name first; keys containing a colon are then joined by trying each suffix after a colon against the discovered names (longest matching suffix wins), and keys that match nothing are dropped - they name skills outside this vault's discovery set, which cannot be ranked anyway. The rule and the drop are documented in skill-usage.ts and docs/mcp.md, so the coverage boundary (private records never count; non-discovered names never join) is stated, not silent.
9. **t_4501c662 - sampling selects PRE-conversion entries over the official types.** A new pure module src/core/bench/longmemeval-sample.ts exports `sampleLongMemEvalEntries(entries, opts)`: abstention entries are excluded FIRST (their count flows to the existing `abstention_excluded` semantics, so the receipt stays honest), the remaining entries are stratified by `question_type` (the distinct present types, sorted ascending - the six official types in real datasets, legacy types in the committed samples), each stratum's allocation comes from largest-remainder (Hamilton) apportionment of the cap proportional to stratum population, clamped to the population, with fractional-remainder ties broken by stratum name ascending. Within a stratum, entries are sorted by `q_id`, reordered by a seeded Fisher-Yates over an own mulberry32 PRNG (the raw seed string hashed by `sha256Hex`, its first 8 hex chars parsed into a uint32; no Math.random, no wall clock), the allocation taken, and the selection re-sorted by `q_id` so downstream order is independent of selection. A cap at or above the population selects everyone; a population of zero after abstention exclusion is a named `LongMemEvalSampleError`, not an empty fixture handed to the converter.
10. **t_4501c662 - the flags are a pair and ride the --recall-floor trace.** `--sample-seed <value>` and `--sample-cap <count>` parse beside `parseRecallFloorFlag` with the same CliError refusal shape; either alone is refused by name (a lone seed would silently select the whole population - the forbidden silent no-op), a non-positive or non-integer cap is refused, and both together require a suite whose registration declares the new `capabilities.sampling: true` (only longmemeval) - otherwise the CLI refuses naming the suite, so the flags can never be silently ignored by a loader that cannot honor them. The loader contract widens with an optional second parameter (`BenchSuiteLoadOptions`) preserving `registerBenchSuite` compatibility; `loadLongMemEvalFixture` gains an options-carrying path and the no-options path stays byte-identical.
11. **t_4501c662 - sampling options fold into run identity with spread-omission.** `benchRunIdentityHash`'s canonical record gains a `sample` record (seed, cap) only when sampling is set: two option sets that produce the same fixture (cap at or above the population) still get different run ids, while runs without sampling hash exactly as before, so pre-change in-flight runs keep resuming (the loud identity guard is reserved for runs whose options actually changed). `BenchCheckpoint` gains the optional `sample` field beside `pinned_knobs`, and `runMemoryBench` validates and folds like `recallFloor` (named refusal before any run state exists). Receipt fields `sample_population`, `sample_selected` and `sample_strata` join `BenchSuiteReceipt` mirroring `abstention_excluded`, and the longmemeval report family gains `sample_selected`, so a run reports honestly what it measured.
12. **t_68ae8a53 - a vendored minimal JSONC editor, not a new dependency.** The repo has exactly one runtime dependency and no JSONC handling anywhere, and the needed edit surface is narrow: read with positions enough to locate top-level keys, insert or replace one entry under `mcp.servers`, remove it, and refuse ambiguity. New leaf module src/core/install/jsonc.ts (sibling of json-merge.ts): a tokenizer covering line and block comments, strings with escapes, trailing commas and literals; edits applied as token-offset splices, never whole-root re-serialization; duplicate top-level keys are a named `JsoncEditError` refusal (upstream refuses ambiguity the same way). Files bearing no comments and no trailing commas keep the existing json-merge round-trip byte-for-byte (every existing pinned-content test holds); the JSONC path activates only when the tokenizer sees comments or trailing commas. A dependency would be the larger, less honest change for this surface.
13. **t_68ae8a53 - shape detection by file, shared by apply and verify.** `resolveTargetShape(parsed)` returns the native `mcp.servers` key when the file carries that object, else the V1 top-level `mcp` - adopting upstream's precedence rule (native declarations win; an existing legacy declaration must not be shadowed). Apply and verify both call the same function, so verify's reconstruction is symmetric with apply by construction and a fresh install can never report drift against itself. The manifest's `owned_keys` string records the shape actually written (`mcp.<name>` or `mcp.servers.<name>`), so uninstall removes exactly what apply wrote. When only `opencode.jsonc` exists it is the config path; when neither exists a fresh install creates `opencode.json` as today (V1 and V2 hosts both read it).
14. **t_68ae8a53 - the doctor probe learns the nested key in the same change.** `JSON_MCP_TOP_LEVEL_KEYS` and `extractFromJsonConfig` learn the dotted `mcp.servers` path, or every healthy V2 install would report "no Open Second Brain command entry found" from a check that is independent of the adapter. Host facts grow nothing: the V1/V2 choice is a property of the on-disk file, and the module's rule is that nothing there reads the machine; the 10-target census pin stays untouched because no target joins or leaves.
15. **Wave-wide house rules.** Every opt-in surface ships default off with a byte-identical-off regression proof (for the adapter, V1-shaped configs are the byte-identical case); failures are typed named errors, never silent fallbacks - the sampler's zero-population case, the JSONC ambiguous-file case, the lone-sample-flag case and the wrong-suite sample-flag case all refuse by name; the tool census, continuity reader/envelope censuses, write-site census, host-facts census and import-cycle ratchet move only in the commits that grow their inputs (none of them grow this wave); no variable is named anything secret-shaped (the redactor and plugin-scanner rules); docs prose uses the full product name and no exclamation marks.

## Risks and open questions

- **Cache staleness on the new knob.** The cap changes result content, so a missing fingerprint fold serves stale rows; the lane mirrors the two mmrLambda folds exactly and the config test pins both.
- **Ranking-behavior drift on the skill offer.** The reorder changes what agents are offered every turn once the flag is on, and `computeSkillOfferId` hashes the offered order, so offer ids shift when usage data shifts - by design, but any fixture pinning an offer id must also pin the usage input and nowMs. The default-off path is byte-identical and the bench-style surface tests cover both modes.
- **Bench identity and resume.** The sampler's spread-omitted identity fold keeps pre-change run ids stable, but a resumed run whose sampling options changed still fails the guard loudly by design; docs say so rather than hiding it. Committed sample fixtures stay untouched - sampling tests build synthetic populations through the existing `entry()` helper so fixture hashes in CI stay pinned.
- **JSONC edge cases.** The vendored editor refuses what it cannot rewrite honestly (duplicate top-level keys); a config it refuses leaves the install flow with a named error and no partial write. The tokenizer's test matrix covers comments in the target region, comments elsewhere, trailing commas and BOM.
- **The user-modified-block guard on first V2-shape apply.** When a native `mcp.servers` object appears in a config the adapter previously owned, the guard reports the file as user-modified and the first re-apply is an operator action; the docs follow the 1.50.0 upgrade-notes convention (the first `--check` after the host upgrades reports drift once; fix is re-apply).
- **Directory plugin loading on V2 hosts.** The wave keeps the file-drop plugin install on the evidence that V2's config-object removal directives presuppose directory loading; if a future host drops it, the plugin would need config-object registration as a follow-up. The adapter's verify path (plugin content compare) surfaces that failure rather than hiding it.
- **Cost of the usage read per turn.** With the flag on, `deriveSkillUsage` reads the whole continuity store once per attach call - precedent-priced by the existing MCP usage operation, absent when off; the docs name the cost and the deferred windowing option.
- **Pre-existing, out of scope:** the atomic write replaces a symlinked config rather than writing through it (V1 paths included); Windows launcher env and BOM handling are already covered by the existing write path and tests.
