# Who wrote what, and how to take it back - implementation plan

Feature branch: `feat/who-wrote-what`. TDD per task, one atomic conventional commit per task, `bun run fmt` + `bun run lint` green before every commit. Tasks 1-3 are independent and run in parallel in separate worktrees; tasks 4-5 run after them. Task 6 is the reconciliation the orchestrator does on the feature branch.

Registration checklist for a new `o2b brain` verb (six places): handler `src/cli/brain/verbs/<verb>.ts`; barrel `src/cli/brain/verbs/index.ts`; dispatcher import + `case` in `src/cli/brain.ts` (the `switch` stays terminated by `default:`); `src/cli/brain/help-text.ts` summary line in `BRAIN_HELP` AND a `VERB_HELP` key; `src/cli/command-manifest.ts` brain group; `docs/cli-reference.md`. Pinned by `tests/cli/manifest-completeness.test.ts` and `tests/cli/help-surface-parity.test.ts`.

Registration checklist for a new MCP tool: `ToolDefinition` in a domain array (model `brain_agent_diff`, `src/mcp/brain/query-tools.ts:713-751`); description <= 300 chars, property descriptions <= 160; `previewBudget` or a >= 10-char exemption reason in `src/mcp/registry-guard.ts` `PREVIEW_BUDGET_EXEMPT`; pins: `tests/mcp/mcp.test.ts:765` (113 -> 114), `tests/mcp/brain-tools-parity.test.ts` `FROZEN_BRAIN_TOOL_NAMES`, `tests/mcp/agent-scope-matrix.test.ts:214` (113 -> 114) plus a `SCOPED_SURFACES` / `PROBE_ENTRIES` classification, `tests/helpers/tool-probe-catalogue.ts:274-276` (`PROBE_ENTRY_COUNT` 99, `PROBE_RECIPE_COUNT` 226, `PROBE_TWO_SIDED_COUNT` 32 - measured after adding the probe), `tests/core/install/tool-ceiling.test.ts:343` (`available_tool_count` 113 -> 114), `docs/mcp.md` prose counts. A tool that reads page content needs a `src/core/search/visibility-surface-registry.ts` row (`tests/core/architecture/visibility-surface-census.test.ts:452`, `MCP_TOOL_POPULATION_SIZE` 48).

- **Acceptance**: after agent A updates a note twice and agent B never touches it, `revert --agent A` plans one `restore` to the pre-A bytes and `--apply <digest>` restores them, takes a `note-revert` snapshot, and appends a `note-write` event with `op: revert`; if B updated in between the plan refuses `interleaved`; if the note changed after A's last write the plan refuses `drift`; a note A created is planned `delete`; applying a stale digest is refused before any byte moves.
