# Observability contract

Open Second Brain records what it did - learning events, recall decisions, served context, session activity - across a small set of file-based surfaces inside the vault. This document is the contract for anyone consuming those surfaces: which events exist, when they fire, what correlates them, what safety guarantees their payloads carry, and how the record shapes evolve. Everything here is verified against the source files named in each section.

## Surfaces at a glance

| Surface | Location | Writer | Format |
|---|---|---|---|
| Brain log | `Brain/log/<date>.md` + JSONL sidecar | `appendLogEvent()` in `src/core/brain/log.ts` | Markdown line + JSONL row per event |
| Continuity store | `Brain/log/continuity/<month>.jsonl` | `appendContinuityRecord()` in `src/core/brain/continuity/store.ts` | one JSON record per line |
| Session lifecycle audit | `Brain/log/session-lifecycle/` | `captureSessionLifecycleEvent()` in `src/core/brain/session-lifecycle.ts` | JSONL audit rows |
| Bench runs | `<runs-dir>/<run-id>/` (default `.open-second-brain/bench-runs/`, gitignored) | `runMemoryBench()` in `src/core/bench/phases.ts` | `checkpoint.json`, per-question results, `report.json` |
| Metrics | `Brain/metrics/<surface>.jsonl` | `appendMetric()` in `src/core/brain/metrics.ts` | one run-level JSON record per line (see `docs/metrics.md`) |

The `prompt_prefix` metric surface measures STRUCTURAL prompt-prefix stability (whether the kernel handed the agent a byte-stable, cache-eligible preamble across a generation pass), never a provider's cache-hit rate the kernel cannot observe. It stores only the SHA-256 hash and length of the prefix, never the raw prompt - the same payload-safety rule as `generation_report`. See `docs/metrics.md`.

## Brain log events

`appendLogEvent()` writes one human-readable line to the daily Markdown log plus a structured JSONL sidecar row. These events are always-on: each one is the audit trail of the operation that produced it, never optional telemetry. Kinds (from `BRAIN_LOG_EVENT_KIND` in `src/core/brain/types.ts`):

| Kind | Fires when |
|---|---|
| `dream`, `promote`, `retire`, `noted-redundant`, `signal-suppressed`, `skip-corrupted-frontmatter`, `reconcile` | the deterministic learning pass runs |
| `feedback`, `apply-evidence`, `force-confirmed`, `reject` | a taste signal or evidence event is recorded |
| `pin`, `unpin`, `rollback`, `merge`, `upgrade` | operator-facing vault maintenance |
| `scan-inline`, `import-session`, `import-claude-memory` | capture and import operations |
| `note` | a narrative milestone is recorded (`brain_note`) |
| `session-lifecycle` | a captured lifecycle event also produced Brain writes |

## Continuity record kinds

Every continuity record shares one envelope, and exactly these eight fields in this order: `schema`, `id`, `kind`, `createdAt`, `sourceRefs`, `payload`, `private`, `redacted`. The table marks how each kind is gated - this is the always-on vs opt-in matrix, verified against the call sites named in the right column.

| Kind | Gate | Emitted by |
|---|---|---|
| `recall_telemetry` | opt-in per call (`telemetry` option/param); the prompt-time hook emitter is gated by `recall_inject_enabled` instead | `packContext` (`mode: context_pack`), `buildPreCompressPack` (`mode: pre_compress`), `brain_search` MCP handler (`mode: search`), `brain_query` MCP handler (`mode: query`, since v0.40.0 - payload carries the query kind only, never the supplied preference id / topic / timestamp), and since v1.46.0 the `UserPromptSubmit` recall-inject hook (`mode: search`, `channel: hook`, mapping its inject / abstain / error decision onto `ok` / `empty` / `error`) |
| `context_receipt` | opt-in per call (`receipt` option/param) | `packContext`, `buildPreCompressPack` |
| `gate_telemetry` | config key `recall_gate_telemetry` (default off) | `brain_recall_gate` MCP handler |
| `negative_recall` | config key `recall_gate_telemetry` (default off - the SAME gate as `gate_telemetry` above, so one config decision governs both observations the recall gate makes) | `brain_recall_gate` MCP handler on the zero-usable-result path only (`emitNegativeRecallTelemetry` in `src/core/brain/gate-telemetry.ts`) - one record per gate call whose caller reported no usable result, carrying the typed corpus verdict (`state`, `complete`, the named `unknown_reason` when the verdict is `unknown`, `reason`) plus the reduced coverage receipt when one could be built (`coverage_digest`, `documents`, `chunks`, `schema_version`, `embedding_signature`, `last_indexed_at`, `scope`, `unindexed_roots`). Two receipt fields are not copied into the payload: `index_path` is deliberately dropped - a host filesystem path is not vault content and these records sync between devices, and the digest already binds it; the `embeddings` census the receipt carries is likewise absent from the payload and likewise bound by `coverage_digest`, so a reader comparing two records still sees a keyword-only index differ from a fully embedded one. Same prompt invariant as `gate_telemetry`: a SHA-256 prefix (`prompt_hash`) and the length (`prompt_chars`), never the prompt. A call with usable results writes NO record, so a corpus statement is never invented for an attempt that had one |
| `generation_report` | opt-in per call (`enable`) or config key `generation_trace_enabled` (default off) | inbound agent report after a generation handoff (`brain_generation_reports` action `record`, `o2b brain generation-reports record`) |
| `mcp_route_latency` | config key `mcp_route_metrics_enabled` (default off) | the MCP server's tool-call seam (`MCPServer.invokeToolHandler` in `src/mcp/server.ts`) - one record per `tools/call` and per CLI-bridge `callTool`; payload carries the tool name, scope, status, duration, and argument KEY NAMES only, never argument values |
| `token_impact` | config key `token_impact_ledger_enabled` (default off) | `brain_token_impact` action `record` (`emitTokenImpact` in `src/core/brain/token-impact.ts`) - one sample per context pack; payload carries the tokenizer-exact prompt-token counts (`baseline_tokens`, `packed_tokens`, signed `delta_tokens`), the `method` label (`exact`/`fallback`), an optional opaque `pack_id`, and the optional modeled inference-avoidance estimate - never raw prompts or recalled text |
| `token_impact_outcome` | config key `token_impact_ledger_enabled` (default off) | `brain_token_impact` action `outcome` (`recordTokenImpactOutcome`) - one first-pass/repair/retry post used only to calibrate the modeled ledger |
| `context_pack_outcome` | config key `context_pack_outcome_enabled` (default off) | `brain_context_pack_outcome` action `post` (`postContextPackOutcome` in `src/core/brain/context-pack-outcome.ts`) - one compact per-sample outcome row for a carried context-pack quality-sample id: first-pass/repair/retry counters plus three STRICTLY SEPARATE token signals (`exact_prompt_token_savings`, `modeled_inference_avoidance`, `observed_provider_tokens`), never merged; payload carries counters + an opaque `sample_id` only, never raw prompts or recalled text, and a caller-omitted field is not invented. One `post` writes THREE records, all joined on the same `sample_id`: this row, a `token_impact_outcome` calibration post, and a `context_pack_evidence` row (both listed separately below and in this table). The thin wrapper `emitContextPackOutcome` returns only this row; the two composed records are written either way |
| `context_pack_evidence` | config key `context_pack_outcome_enabled` (default off - the same gate as the outcome row it accompanies) | composed by every `brain_context_pack_outcome` action `post` (`recordContextPackEvidence` in `src/core/brain/context-pack-evidence.ts`) - one row per outcome row, joined on the same `sample_id`, carrying the evidence the kernel reads back off disk (the `context_receipt` that id names: `final_text_hash`, `item_count`, `final_text_chars`) and a closed `verdict` over the acting agent's optional claim: `match`, `mismatch`, `unclaimed` (evidence obtained, nothing asserted), or `unresolved`. A `mismatch` lists the drifted fields and is RECORDED, never resolved - the outcome row is neither rejected nor silently corrected by it. An `unresolved` verdict names why through a separate token, `sample_absent` (the log was read and holds no such receipt) or `evidence_unreadable` (the log could not be read at all), so absence is never reported as inability. Payload carries those tokens + the opaque `sample_id` only, never raw prompts or recalled text. NOT an independent attestation: the agent id on the row is self-asserted and this same process wrote the receipt it now reads. The `post` response echoes the payload under `evidence`, so a contradicted claim is visible to the poster and not only to a later reader |
| `ingest_dedup` | always-on, fail-open; written ONLY by a run that actually dropped something | the three ingest runs that drop an item on an exact sha-256 `dedup_hash` collision: `captureSessionLifecycleEvent`, `scanInline`, `importSession` (`emitIngestDedupReport` in `src/core/brain/dedup-telemetry.ts`) - one record per run, payload carries the `surface`, the run's `exact_deduped` total, and a `by_source` map keyed by the session id or vault-relative note path being re-ingested. A run that deduped nothing writes NO record, so a real zero stays distinguishable from an absent measurement. Every count is an EXACT-hash drop; the semantic detectors nominate merge candidates and never drop, so no semantic figure appears here |
| `session_turn`, `session_summary_node` | always-on within its operation | session-recall import (`src/core/brain/session-recall.ts`) - the write IS the operation |
| `pre_compact_extract` | always-on within its operation | explicit pre-compact extraction (`src/core/brain/pre-compact-extract.ts`) |
| `source_invalidation` | always-on within its operation | source drift detection (`appendContinuitySourceInvalidation`) |

Session lifecycle capture (`captureSessionLifecycleEvent`) writes audit rows and Brain log events, and no continuity record at all unless the event actually dropped a repeat - in which case it writes exactly one `ingest_dedup` record. Both halves of that boundary are pinned by regression tests (`tests/core/brain/continuity-emit.test.ts` for the silent path, `tests/core/brain/dedup-telemetry.test.ts` for the dedup path).

## Schema version and evolution rule

Since v0.39.0 every new continuity record is stamped `schema: "o2b.continuity.v1"` (`CONTINUITY_SCHEMA_VERSION` in `src/core/brain/continuity/types.ts`).

- Records written before the stamp existed carry no `schema` field; every reader treats `undefined` as v1. Existing JSONL files are never migrated.
- Additive optional fields do NOT bump the version. Renames, removals, or semantic changes bump to `o2b.continuity.v2`.
- The record id (`recordId()`, sha-256 over kind + createdAt + sourceRefs + payload) deliberately EXCLUDES the schema field, so identical records keep identical dedup ids across the stamp transition. Locked by a known-answer test.
- Consumers should go through the read-model (`src/core/brain/continuity/read-model.ts`), which absorbs the version dispatch, lifts `session_id`/`turn_id` into first-class fields, and applies the masking policy below.

## Correlation IDs

| Field | Where | Stable join? |
|---|---|---|
| `id` (`ctn_<stamp>_<sha16>`) | every continuity record | yes - content-hash dedup id |
| `createdAt` | every continuity record | ordering key (store sorts by `createdAt`, then `id`) |
| `sourceRefs[].id` / `.path` | continuity records | joins records to vault artifacts |
| `session_id`, `turn_id` | payloads of session-scoped kinds; lifted by the read-model | yes - the cross-surface session join |
| `handoffKind`, `handoffRef` | `generation_report` payload `handoff`; lifted by the read-model | yes - joins a generation report to the write-session / context-receipt / dream run it traced |
| `timestamp` + `agent` | Brain log events | per-event attribution |
| `agentId`, `isSidechain` | `SessionTurn`, from a transcript that records delegation | yes - the only thing separating a delegated sub-agent's turns from its parent's, because a sub-agent transcript reuses the PARENT's session id |

Multi-agent vaults attribute writers via per-agent identity (`brain_agent_query`). Delegated sub-agents are correlated as of v1.49.0, and by the additive route this sentence used to promise: `SessionTurn` carries an optional `agentId` and an optional `isSidechain: true`, both emitted only where the transcript records them, so a flat transcript keeps its pre-delegation shape byte for byte. A sub-agent transcript reuses its PARENT's session id, so those two fields are the only thing separating the two agents' turns. The `SubagentStop` hook records the close under `<delegator>-sub-<agent-id>`; the `agent_transcript_path` the event also carries is deliberately not persisted, being a machine-local host path.

## Payload safety

Every continuity payload passes `safeContinuityPayload()` (`src/core/brain/continuity/redaction.ts`) before it reaches disk:

- `<private>...</private>` regions are stripped and replaced; the record is flagged `private: true`.
- Secret-shaped tokens are redacted to `***REDACTED***`; the record is flagged `redacted: true`.
- The sanitized payload is deep-frozen; nothing mutates it after the flags are computed.
- `gate_telemetry` never stores the raw prompt by construction - only a SHA-256 prefix (`prompt_hash`) and the length (`prompt_chars`). The test suite asserts this against the persisted files, not just returned values. `negative_recall` shares that construction (same module, same hash helper) and adds one rule of its own: the coverage receipt it carries drops `index_path`, so no host filesystem path replicates with the vault.
- `generation_report` follows the same rule: the handoff prompt is hashed and counted but never persisted - only `prompt_hash` (full SHA-256 hex) and `prompt_chars` land on disk, plus token counts. The kernel never calls an LLM; the report is the agent's INBOUND record after it performed a generation for a brain handoff, so the local token estimate (`local_estimate.input_tokens`) is always present while the agent-reported `usage` block is present only when supplied - absent is reported as absent, never fabricated. A grep-guarded regression test pins that no `fetch`/provider HTTP call exists under `src/core` for this feature, and a persisted-file assertion confirms no raw prompt survives.
- `mcp_route_latency` records the route (tool name), MCP scope, status, duration, and the sorted set of argument KEY NAMES only - the tool's own JSON-Schema property names, never operator-supplied argument values - so no prompt, note body, or preference id can land on disk. A persisted-file test asserts key names survive while values never do.
- The masking policy lives in the read-model (`src/core/brain/continuity/read-model.ts`) and governs only the readers that go through it: records flagged `private` are dropped by default and kept only on explicit request; masked text is never un-masked. That is FOUR modules - the `o2b brain continuity` verbs (trajectory export and listing), the bench harness, `brain_event_trace`, and skill-usage aggregation. Twenty-one other modules call `listContinuityRecords` on the store directly and see raw records: no `private` drop and no schema-version dispatch. The policy is read-model-wide, NOT store-wide. Both lists are asserted by name in `tests/core/brain/continuity/reader-census.test.ts`, which fails when a module joins or leaves either set, and both COUNTS are pinned there as equalities rather than floors - the direct floor used to sit at twenty against a reality of twenty-one, which is how the number in this sentence came to be wrong. Auditing the direct readers is tracked separately.
- A hook's `tool_response` is READ and never written. Lifecycle capture consults it to decide whether the call it is reacting to actually succeeded - a failed `brain_feedback` must not be replayed, because replaying it mints the record the tool declined to create - and the decline is counted rather than swallowed. The response body itself is arbitrary tool output and never reaches a payload, so declaring it in the hook contract costs nothing on disk.
- `private` is the ONLY visibility signal a record carries, and it is inferred from a `<private>` region in the payload rather than declared. A caller-declared `scope` field was built for this envelope and removed before release: nothing in the codebase could supply one - no tool argument, no command-line flag, no config key and no library entry point - and its single vocabulary member would have narrowed a record's visibility rather than widened it, since a declared scope is dropped by every reader that does not name it. Adding a declaration to the envelope is a schema change; `tests/core/brain/continuity/record-envelope.test.ts` pins the eight fields and their order so the next attempt has to be argued for.

## Fail-open rules

Telemetry must never block or fail the primary operation. The guarantee is structural, not conventional: gated surfaces route through `emitGatedTelemetry(gate, build)` (`src/core/brain/continuity/emit.ts`):

- gate off (`undefined`/`false`/`null`): the build thunk is NEVER invoked - no payload object, no hash, no write on the no-consumer path;
- a throwing thunk or store write is swallowed and reported as `null`; the context pack, pre-compress pack, search response, and recall-gate decision all complete normally with the telemetry field simply absent.

No-consumer regression tests cover each gated surface, so a future call site cannot silently regress to eager payload construction. Writers whose continuity append IS the primary operation (session-recall import, pre-compact extract) stay fail-fast on purpose - failing silently there would lose user data, not telemetry.

## Reading the surfaces

- `brain_recall_telemetry` (MCP) and `o2b brain recall-telemetry list|summary|gate-list|gate-summary` aggregate recall and gate records. Since v1.46.0 every `recall_telemetry` payload carries a `channel` naming the seam the recall came through - `mcp`, `cli`, or `hook`, a closed set. It is a property of the emit site rather than a caller argument: the MCP handlers stamp `mcp`, `o2b brain context-pack --telemetry` stamps `cli`, and the recall-inject hook stamps `hook`. Every emit site must name one, enforced at build time, so no new record lacks it. `channel` is clip-protected alongside `session_id` and `agent_id`, so an output-budget clip may not drop it. Filter on it with the `channel` argument (MCP) or `--channel` (CLI) on `list` and `summary`, and read the `by_channel` rollup on `summary`; a channel with no record is absent from that rollup rather than reported as `0`. Records written before v1.46.0 carry no `channel` at all and are never migrated, so they count in `total` / `by_mode` / `by_status` but fall into no `by_channel` bucket, and any `channel` filter excludes them. `o2b brain doctor` crosses the rollup against per-channel install state and reports `recall-channel-silent` (installed, expected to deliver, silent for 30 days) or `recall-channel-unmeasured` (one half of that cross could not be read - the latter rides the `uncertain` stream and does not affect the exit code).
- `brain_recall_telemetry` `operation: "cost"` (MCP) and `o2b brain recall-telemetry cost` fold WRITE volume against the read telemetry above: memory-write ops (Brain-log `feedback`/`apply-evidence`/`note` verbs plus `host_memory_write` continuity records) are counted per period and reported alongside reads as a write-vs-read ratio, a `write_heavy` flag, and a rough weighted cost signal. Weights (`--write-cost`/`--read-cost`, default 1 each) model "some tools charge on write, some on read"; `--write-heavy-ratio` (default 1) sets the write-heavy threshold. Read-only; period-scoped by `--since`/`--until`. `brain_create_note` file creation emits no telemetry event today and is not counted.
- `brain_context_receipts` and `o2b brain context-receipts` inspect served-context receipts.
- `brain_route_metrics` (MCP, `operation: "list"|"summary"`) reads route-level MCP tool latency. `list` returns raw `mcp_route_latency` records (filter by `tool`/`status`/`since`/`until`/`limit`); `summary` rolls each tool up into count, error count, and min/avg/max plus p50/p95/p99 latency, ordered slowest-first so an operator can identify which endpoint blocks an agent turn by route rather than by aggregate benchmark. Records are emitted only when `mcp_route_metrics_enabled` is on (default off); read-only.
- `brain_token_impact` (MCP, `operation: "record"|"outcome"|"list"|"summary"`) is the durable value-of-memory ledger. `record` posts one context pack's prompt-token delta (`baseline_tokens` − `packed_tokens`, labelled `method: tokenizer|heuristic` — how the CALLER produced the counts, never how accurate they are; the ledger counts nothing itself and verifies neither. Samples written under the retired `exact`/`fallback` labels are still read and classified) plus an optional modeled inference-avoidance estimate (`modeled_avoided_inferences` × `modeled_tokens_per_inference`); `outcome` posts a `first_pass`/`repair`/`retry` result. `summary` keeps the two ledgers STRICTLY SEPARATE: `prompt_token_delta` reports the net/saved/added tokens with a per-`method` split (so a tokenizer-produced count is never averaged in with a heuristic estimate), while `modeled_inference_avoidance` reports the raw modeled figure and a `calibrated_savings_tokens` dampened by the observed first-pass rate from posted outcomes (null until an outcome exists — uncalibrated, not zero). `list` returns raw samples (filter by `pack_id`/`method`/`host`/`since`/`until`/`limit`); `summary` accepts `max_samples` to bound aggregation. Writes are emitted only when `token_impact_ledger_enabled` is on (default off) and are payload-safe (counts + opaque `pack_id` only, never prompts or recalled text); `list`/`summary` read regardless of the gate. Aggregates are recomputed from the continuity store on every read, so they survive restarts.
- `brain_event_trace` (MCP) and `o2b brain event-trace` join the Brain log to the continuity store: given a logged event (by day, `--at` stamp, kind, or `--session-id`), they resolve the continuity records attached to it via the stable correlation ids above (`session_id`, `turn_id`, and artifact `sourceRefs`), so an operator can answer "which context was supplied to this action?" from one surface. Each attached record reports `joinedBy` (`session` / `turn` / `artifact`); open the full record through the per-kind readers (`context-receipts show`, `recall-telemetry`, `generation-reports show`). Read-only; `private` records are dropped unless explicitly kept.
- `brain_generation_reports` (MCP, actions `record`/`list`/`summary`) and `o2b brain generation-reports record|list|summary|show` post and read inbound LLM generation traces. `summary` rolls up call counts, the always-present local token estimate, agent-reported usage where present, and a per-path linkage map so a memory path resolves back to the generation reports that produced or consumed it.
- `o2b brain continuity export --format atof|atif` renders the store as standard trajectory formats (ATOF JSONL event stream; ATIF v1.7 one document per session) for replay and eval tooling. Read-only; `private` records never reach an export file. Mapping decisions: `docs/brainstorm/memory-observability-suite/atof-atif-mapping.md`.
- `o2b brain bench memory` measures memory quality over disposable fixture vaults and reports quality, latency, context cost, and failure modes as separate families (`o2b.bench.v2` report schema). Beyond the retrieval categories it scores three failure modes the retrieval questions cannot see: `proactive_recall` drives `decideRecallInject` over the fixture and reports `know_to_ask_failure_rate` and `false_fire_rate` (both denominated in decisions, so a strategy that always injects scores worse than one that abstains correctly); `write_fidelity` grades the provenance that survives the shipped extraction, insertion and dedup path with no model call; `source_isolation` asserts on delivered context-pack contents under a requested owner scope and gates at zero. `context_cost.avg_injected_tokens` is `estimateTokens` over the strings the bench actually injected — the suite's one token estimator. Two things the numbers do NOT say: `recall_inject_enabled` is off by default, so the proactive metric describes a capability rather than delivered behaviour, and `integrity.owner_scope_delivery` is off by default, so an isolation fixture must set it to `fail` or the gate is vacuous. The committed baseline is `tests/fixtures/bench/failure-modes.baseline.json`, compared by `tests/core/bench/failure-modes-baseline.test.ts` inside the ordinary `bun test` gate.

Consumers should treat unknown record kinds and unknown payload fields as fine - skip what you do not recognize (the store and read-model already behave this way).
