## 1. The decide pass as it is

**Orchestration.** `decideTopicPlan` (`src/core/topics/decide.ts:58`) resolves the decision-model config (`decide.ts:65-69`), returns empty when status ≠ `active` (`decide.ts:70`) or when every dream use is `off` (`decide.ts:71-73`), takes the view-writer gate (`writerGate`, `decide.ts:76-81`), reads the store outside the planning lock (`catchUpWhere`, `decide.ts:86-87`; an incomplete read returns empty, `decide.ts:87`), builds candidates (`topicCandidates`, `decide.ts:93`), builds the **deterministic plan itself** (`planTopics`, `decide.ts:95-104`) and then runs seven uses in fixed order against a per-use share of one 20 s budget (`DECIDE_PASS_BUDGET_MS = 20_000`, `decide-shared.ts:33`; order at `decide.ts:133-141`; share arithmetic `useShareUntil`, `decide-shared.ts:85-88`). **Budget.** Pass budget `deadlineMs`/20 s (`decide.ts:116`), per-request timeout clamped to the use's share (`requestTimeoutMs`, `decide-shared.ts:186-188`), the request floor holds per attempt (`requestFloor: true` in `requestOptions`, `decide-shared.ts:294-310`; `run.ts:224-231,322-341`). - `event_kind` → subject record id, input record text + topic title, schema `choice` of the 7 kinds, apply = the `verdict-writes.ts:117-145` derive block (today that block is the natural `apply`).

## 2. The decision model chain

- **Configuration**: flat `decision_model_*` machine-config keys with `OPEN_SECOND_BRAIN_DECISION_MODEL_*` env overrides (`src/core/decision-model/config.ts:1-30,118-125`). Statuses: `disabled`, `invalid`, `no_key`, `disabled_by_vault`, `active` (`config.ts:840-845`). Chain: `decision_model_providers` (ordered preset list) with per-entry `decision_model_providers_<preset>_base_url|_id|_env_key` (`config.ts:356-407,728-824`). Modes per use: `decision_model_uses` `use:mode` comma list (`config.ts:170-200`), `off/shadow/enforce` (`contract.ts:73`). `enforce` is held to `shadow` unless the entry is tuned (source table, local thresholds store, or measured mark): `holdToProfile` (`config.ts:107-116`), `entryTunedGate` (`config.ts:312-322`).
- **Request function**: `runDecision` (`src/core/decision-model/run.ts:208`) — the one entry point every use goes through (`run.ts:1-24`). Chain built by `buildChain` (`run.ts:168-201`), adapters by `makeEntryDecisionProvider` (`provider.ts:47-112`; an entry without endpoint or required key is `null` = not configured). An injected `provider` (tests) replaces the whole chain (`run.ts:176-180`).
- **Privacy/egress**: `mayShareRecord` — a private record leaves only when every chain entry is loopback or the use is opted in via `decision_model_private_uses` (`egress-guard.ts:97-113`); a mixed local/hosted chain counts as hosted (`egress-guard.ts:7-11`); head fields gated by `shareableHeadFields` (`egress-guard.ts:122-135`); `<private>` regions always stripped (`decide-shared.ts:8-10`). Endpoint checks: no userinfo in URLs (`config.ts:518-523`), `assertHttpEgressEndpoint` with `decision_model_allow_insecure_http` (`config.ts:530-539,773-781`), model must be pinned not `latest` (`config.ts:501-503`).
- **Failure modes**: typed `DecisionDegradeReason` = `cost_gate | budget | egress_refused | timeout | network | invalid_reply | http_<status>` (`contract.ts:97-104`); only `network`/`timeout` fall through to the next chain entry (`run.ts:203-206,353-373`); one retry max on 408/409/429/5xx with `retry-after` (`transport.ts:26-31,143-176`); reply capped at 1 MiB and error bodies never echoed (`transport.ts:24,114-123`). Never throws (`run.ts:21-24`).
- **"No model configured" vs "model failed"**: a caller distinguishes them by `cfg.status` (`no_key`/`disabled` = not configured; `config.ts:840-845`) plus the resolved mode (`decisionModelModeFor`, `config.ts:886-892`) versus `runDecision`'s `status: "degraded"` + reason (`run.ts:80-100`). `status: "off"` covers both config-off and an empty chain (`run.ts:217-226`) — the two are *not* distinguished at the run level, only at the config level.
- **Queue executor for one item at a time?** Yes, structurally: `runDecision` is stateless per call, takes one request (state + questions) and returns one typed result; a queue executor for closed questions could call it once per taken item with the item's payload as the state and one question built from `answer_schema`. The named function: `runDecision` (`run.ts:208`). Two frictions: (a) `runDecision` records an accounting `decision_model_call` per attempt (`run.ts:233-274`) and applies a daily cost gate keyed to a vault (`run.ts:285-297`), which is fine; (b) its mode is per-*use*, not per-item, and the verdict thresholds (`use-thresholds.ts`) are keyed by model — a queue answer has no threshold concept today (`answerWork` only validates shape, `queue.ts:583-591`).

## 3. Rule-produced text a model would write under the new design

- **Wording a rule/topic from several signals — topic title and goal**: `draftTitle` and `draftGoal` (`src/core/topics/plan.ts:324-368`): most frequent subject words, compound-aware, first-record tie-break; goal = the first member's text clipped. Inputs: the group's member texts. Stored: on the create record's `title`/`goal` (`plan.ts:585-593`), written by planning's create batch under the planning lock. **No draft state** — the create is written directly; the only pre-write check is the model veto from `topic_new`.
- **Merging two rules (topics)**: no merge text is produced by a rule today at all. The rule only *proposes*: `reviewTopics` (`plan.ts:466-490`) computes Jaccard pairs; `topic_same` verdicts annotate them (`plan.ts:440-463`); the proposal is listed to the user and applied only on confirmation (`src/core/topics/review.ts:5-9`). The merged wording would be entirely new text work.
- **Topic summaries / rollup summaries**: the rollup ladder emits a `needs-llm-step` envelope (`prompt`, `schema_hints`, `target_path`; `src/core/brain/llm-step.ts:28-49`; ladder rungs fact→rollup→identity `src/core/brain/rollup-ladder.ts:184-185`, envelope built at `rollup-ladder.ts:232-235`). Nothing consumes it (`dream-work-queue/design.md:9`; brainstorm "nothing reliably brings an answer back", `agent-neutral-dream/brainstorm.md:30`). The queue now holds it: `produceRollupWork` copies `entry.envelope.prompt/schema_hints/target_path` into the item payload (`src/core/brain/dream-queue/rollup-work.ts:146-153`), and the `rollup-summary` operation's `apply` **refuses** (`rollup-work.ts:72-77`). The answer schema is the whole note: YAML frontmatter with a `kind` key, then body (`rollup-work.ts:34-51`). `currentInput` re-hashes the evidence facts that still exist; `null` (subject gone) when none survive (`rollup-work.ts:58-65`). Draft state for a rollup note: none — today the note exists only as an envelope; the target path is never written by a rule.
- **Human-readable page text**: the weekly history pages render deterministically from stored `log`/`history-verdict` records (`src/core/view/pages.ts`, referenced from `decide-history.ts:7`; the verdict decides only keep/hide, `verdict-writes.ts:212-241`). The page prose itself is a rule-render, and is *derived* (recomputable), not stored — a model-written page would need a new storage home.
- **Existing draft/pending/review mechanisms to reuse**: (a) `question-resolved` / `milestone-done` proposal records the fold shows as "looks answered"/"looks done, confirm" (`verdict-writes.ts:5-14`) — the closest existing "draft with author" pattern (`authority: "model"` plus `verdict` body naming the model, `verdicts.ts:21-53`); (b) the `needs-llm-step` envelope spine with a durable `WriteSessionEnvelope` superset backed by a session record (`llm-step.ts:15-19`); (c) skill-page drafts, which are "envelope-mediated" and structurally validated after the agent returns (`src/core/brain/skill-page-drafts.ts:29-31,96-97`); (d) the queue's own `dream-work-answer` with `agent` and `model` fields (`dream-queue/records.ts:60-69`) — provenance is already part of the answer record. There is **no generic "draft" state** for topic records, rollup notes or pages; "applying drafts automatically is a setting" has no existing hook.

## 4. The queue as implemented

Registered operations (one, at module load): `rollup-summary` (`src/core/brain/dream-queue/rollup-work.ts:67-78`), `closedPredecessor: "release"`. Registration: `registerDreamWorkOperation` into a module `Map`, returning the remover; duplicate names throw (`src/core/brain/dream-queue/operations.ts:44-55`); lookup `dreamWorkOperation` (`operations.ts:58-60`); the fold reads only the traits via `dreamWorkTraits` (`operations.ts:63-65`, `fold.ts:347-349`); an unregistered operation is `unknown_operation`, never ready (`fold.ts:406,419`). `src/core/brain/dream-queue/status-view.ts:9` imports `rollup-work.ts` so every surface registers production operations before reading.

Core functions (`src/core/brain/dream-queue/queue.ts`):
- `produceWork(queue, spec): {id, created, partition}` (`queue.ts:422-433`); item body/id (`queue.ts:401-419`); partition = most private source (`dreamWorkPartition`, `queue.ts:396-398`).
- `takeWork(queue, {run, budgetMs?}): TakeResult` (`queue.ts:466-476`) — lock contention answers `{item: null, reason: "busy"}`; picks the first ready, due, held-partition item, settles first, rereads the input (supersede/cancel on change, `Step.recheck`, `queue.ts:336-368`), writes a lease at `generation+1` with `owner_revision` and a 15-minute expiry (`DREAM_WORK_LEASE_MS`, `constants.ts:61`; `queue.ts:493-501`), rechecks the fold after the lease to narrow the stale-lock double-lease window (`queue.ts:504-507`; design risk `dream-work-queue/design.md:122`).
- `answerWork(queue, {item, generation, value?|text?, agent, model}): AnswerResult` (`queue.ts:545-611`) — idempotent same-receipt accept (`queue.ts:558-560`); refuses when not the newest live generation (`queue.ts:567-576`), lease from a previous owner (`queue.ts:574-576`), unknown operation (`queue.ts:577-578`), open predecessor (`queue.ts:579-582`); schema failure = `failed` attempt with backoff (`queue.ts:583-591`; backoff table `constants.ts:54-59`); input recheck before commit (`queue.ts:592-598`); writes the answer with `agent`, `model`, `receipt` (`queue.ts:600-610`).
- `applyAccepted(queue): {applied, failed}` (`queue.ts:621-648`) — settles, then for every `accepted` item in queue order calls the operation's `apply` and writes `dream-work-applied` with the effect ids; an `apply` throw is collected, not fatal (`queue.ts:633-644`).
- `releaseWork` / `retryWork` / `cancelWork` (`queue.ts:653-687`; retry/cancel are human authority, `records.ts:253-258`).
- `readDreamWork`, `producedItems`, `queueStatus`/`queueStatusAt` — no gate, no writes (`queue.ts:177-183,439-444,748-872`; status carries `executor: false`, `queue.ts:735,839`).

**`rollup-summary`'s `apply` does this**: throws `"rollup-summary: no executor in this version applies a rollup answer; the item stays accepted until one exists"` (`rollup-work.ts:72-77`) — so an accepted rollup answer is collected into `applyAccepted`'s `failed` list every pass and surfaced as the `dream-queue-apply-failed` warning (`src/core/brain/dream-queue/pass.ts:51-64`).

**How a new operation is registered**: implement `DreamWorkOperation` (`operations.ts:30-42`: `name`, `closedPredecessor`, `validate(answer) → reason|null`, `currentInput(item, context) → {input_hash, payload?, evidence?}|null`, `apply(item, answer, context) → effect ids`, idempotent by item id, `operations.ts:36-41`) and call `registerDreamWorkOperation` at module load from a module every queue-reading surface imports (the pattern `status-view.ts:9` establishes); tests register fixtures through the same call and remove them in `finally` (`operations.ts:6-10`; the design statement `dream-work-queue/design.md:67`).

Pass integration: the live owner pass opens the queue (`openQueuePass`, `pass.ts:31-48`; chosen in `dream.ts:236-238` only when the owner gate passes and the brain is store-served), applies at the top (`applyAtPassStart`, `pass.ts:51-64`, called `dream.ts:392`), produces rollup work beside the log write (`produceAtPassEnd`, `pass.ts:67-90`, called `dream.ts:694`), and reports `model_work: {produced, waiting, applied}` (`withModelWork`, `pass.ts:93-107`). A dry run/preview never reaches the queue (`pass.ts:4-6`).

## 5. MCP

- **Tool registration**: tools are static `ToolDefinition` objects assembled in `buildToolTable(scope)` (`src/mcp/tools.ts:510-625`) — name, description, `inputSchema`, optional `outputSchema`, `kind` (`read`/`write`, write-mode-dominant, `tool-contract.ts:285-311`), optional `previewBudget`/`hidden`, and a `handler(ctx, args, onProgress)` (`tool-contract.ts:344-348`). Dispatch: `MCPServer.handleRequest` → `tools/call` (`src/mcp/server.ts:603-608`), `findTool` (`tools.ts:627-640`). New tools are added to the `all` array in `buildToolTable` (grouped spreads at `tools.ts:571-612`); the registry guard audits descriptions/budgets/schemas at test time (`src/mcp/registry-guard.ts`).
- **Profiles and the writer-only server**: profiles pair a `ToolScope` with an optional `RuntimeCapabilityWindow` (`src/mcp/profiles.ts:22-27`); `resolveToolSurface` merges explicit scope/window over the profile and reports `unknownProfile` for the caller to refuse (`profiles.ts:129-153`). The window mechanism (`allowedTools`/`disabledTools`/`maxTools`) is exactly what could expose only three queue tools: a new profile entry with `window.allowedTools = [take, answer, finish]` (`profiles.ts:54-77` shows the shape for `recall`/`minimal`). Note `allowedTools` windows always retain `second_brain_capabilities` (`profiles.ts:12-15`), so "three tools and nothing else" is really "three + the capability diagnostic" unless the profile mechanism is extended. The `writer` *scope* filters to a fixed 5-tool set (`tools.ts:493-499,614`), and the writer-only server is a separate registration built by `buildPayload`: `o2b mcp --writer-only --vault …` (`src/core/install/payload.ts:103-108`; flag alias `--writer-only` → `--scope writer`, `src/cli/main.ts:1017-1031`; server keys `open-second-brain` / `open-second-brain-writer`, `src/core/install/json-merge.ts:28-29`). A queue executor could be a third registered server entry running `o2b mcp` with a new narrow profile/flag, following the `writer` precedent.
- **Caller identity and authority**: per-request `RequestIdentity {agent, via: "token"|"shared-key"}` minted by the HTTP transport from a presented bearer token/shared key (`tool-contract.ts:129-142,253`); stdio and the CLI bridge present no credential and keep the config-derived identity (`token-cli.ts:47-52`). Tools read it off the per-request context (`tool-contract.ts:246-253`); `reach` (`TransportReach`) is resolved fail-closed via `contextReach` (`tool-contract.ts:360-362`), and below local reach private data is withheld at dispatch (`server.ts:604-607`). The dream owner gate itself is not a tool-level check — a queue tool would call `assertDreamOwner`/`assertDreamOwnerOn` inside its handler, as the queue entry points do (`queue.ts:188-209`).
- **Per-run credential check**: token map read by `tokenSourcePath` (device-config `mcp-tokens.json` first, per-vault file fallback; `src/mcp/token-source.ts:48-50`, store at `src/core/brain/secrets/token-store.ts`), matched per request by `resolveMcpToken` (`token-source.ts:59-65`; used in `http.ts:515`). Minting: `mintAgentToken` (`token-store.ts:182-212`), surfaced by `o2b mcp token mint --agent …` (`src/cli/bootstrap/token-cli.ts:22-25`) and by `o2b bootstrap --target … --token` (`src/cli/bootstrap/run.ts:4-8`), with a shown-once notice and the HTTP-vs-stdio boundary sentence (`token-cli.ts:55-73`). A run-scoped credential for the executor session is a new *kind* — today a token is a long-lived per-agent credential, not a lease-scoped one; the nearest scoping primitive is the lease record itself (`owner_revision` + `expires_at`, `records.ts:52-58`).
- **What the server does at initialize** that an isolated executor session must not trigger: `handleInitialize` (`server.ts:648-675`) resolves the agent identity (reading the machine config; a read failure is rendered into the instructions, `server.ts:651-658`) and builds the instruction text (scope, capability report). `notifications/initialized` flips no internal state (`server.ts:596-598`). In *this* branch no hook, capture or session record runs at initialize — not found. The change design adds the day-check to a successful `initialize` for hook-less clients (`agent-neutral-dream/brainstorm.md:76`), so the isolated executor's server (or its env marker) must be excluded from that future check — the mechanism for that exclusion does not exist yet (see §7).

## 6. Launching an agent from the command line

- **Subprocess precedents**: (a) keyless host probes — `probeHost` runs `<bin> mcp list` (Codex, Copilot CLI) via `createHostProbeRunner` with `Bun.spawnSync`, a 10 s cap, an injectable runner seam `setHostProbeRunner`, and named skips for binary-missing/probe-failed (`src/core/install/host-probe.ts:158-243,293-323`; probe specs `src/core/runtime/host-facts.ts:539-545,560-566`). (b) `codex mcp add <name> [--env K=V …] -- <command> <args…>` as a registration mutation (`src/core/install/adapters/codex.ts:267-289`). (c) discipline install writes the Hermes cron jobs file `~/.hermes/cron/jobs.json` (env-overridable `OSB_HERMES_JOBS`; `src/cli/discipline-install.ts:20-40`). (d) the detached self-worker: `spawnSelfDetached` + `detachedSpawnOptions` + `o2bCommand`/`selfCommandFor` — absolute exec path, never a PATH lookup, `setsid`, unref'd, optional stderr log (`src/core/maintenance/o2b-command.ts:73-99,149-223`) — the closest template for a bounded one-shot executor launch. (e) Tests drive subprocess seams via injection (`setHostProbeRunner`, `tests/core/install/host-probe.test.ts`; Copilot's runner seam, `src/core/install/adapters/copilot-cli.ts`).
- **Known hosts' non-interactive invocation forms**: not found. The code and `RUNTIME_FACTS` record only registration/probe forms (`mcp list`, `mcp add`); no `-p`/`exec`/headless prompt form for any host is recorded anywhere in `src/` or `docs/`. The setup-verification step (brainstorm item 10) has no existing form table to copy; it would have to establish one.
- **Machine-local config keys, definition and validation**: the machine config is a flat `Record<string,string>` discovered by `discoverConfig` (`src/core/config.ts`; env override `OPEN_SECOND_BRAIN_CONFIG`, `src/core/install/env.ts:50-54`). Existing machine-local keys read in `src/core/config.ts`: `mcp_tool_profile` (`config.ts:784-789`), `install_hook_timeout_seconds`, `skills_dir` (`config.ts:801-808`); decision-model keys resolve through `envOrConfig(env, config, "OPEN_SECOND_BRAIN_DECISION_MODEL_*", "decision_model_*")` (`decision-model/config.ts:118-125`) with per-key validation collecting into `errors` and status `invalid` (`config.ts:27-29`, e.g. `parseDecisionModelUses` `config.ts:170-200`). A `dream_launch_command`-style key fits this pattern; validation conventions (never echo secret values, name the key in every error) are established at `decision-model/config.ts:98-98,505-517`.
- **Keeping a setting out of the synced settings**: the synced/shared settings are the store's `setting-*` records with a closed key list `SETTING_KEYS` (`src/core/store/constants.ts:211-228`), folded by `foldSettings` — a machine-local key simply never enters that list, exactly how `decision_model_*` and `mcp_tool_profile` stay machine-local today. The design says it directly: launch commands are machine config "because a synced command would run on another machine" (`agent-neutral-dream/brainstorm.md:89`). The install-settings module additionally documents the tier rule for generated artifacts (vault `_brain.yaml` > machine config > compiled default; no environment tier) (`src/core/install/settings.ts:1-57`) — a launch command must not ride the vault tier.

## 7. Recursion and capture guards that exist today

- **Env markers found**: `OPEN_SECOND_BRAIN_SESSION_ID` — names the writer's session so topic records are stamped and neighbour updates are scoped (`src/core/agent-context/session-identity.ts:54,78-90`); it is an identity marker, not a suppressor. `OPEN_SECOND_BRAIN_SESSION_CAPTURE_DEFER` — only switches the session-capture hook between deferred worker and inline capture (`hooks/session-capture.ts:83-85`); it does not suppress capture. `OPEN_SECOND_BRAIN_CONFIG` — parameterises children (`install/env.ts:53`). Hook-level tuning vars exist (`ANSWER_QUOTE_BUDGET_MS`, `O2B_REMINDER_STATE_DIR`, `O2B_MCP_DRAIN_MS`, `OPEN_SECOND_BRAIN_HOST_SETTINGS_BACKUP`).
- **An environment marker that suppresses hooks or session capture wholesale, or that dream sets to make its own sessions invisible: not found.** The design's "a marker in its environment prevents recursion but grants nothing" (`agent-neutral-dream/brainstorm.md:91`) has no existing implementation to extend.
- **What does guard capture today is config, not env**: the capture-boundary matcher decides `capture | ignore | stateless` per session id/transcript path from `_brain.yaml` `sessions.ignore_patterns` / `stateless_patterns`, and suppresses message text by regex, applied before extraction in both the live seam (`session-lifecycle.ts:236`) and batch import (`src/core/brain/capture-boundary.ts:1-30,80ff`). The hooks themselves fire by host matcher (`hooks/hooks.json` PostToolUse/Stop matchers) and check nothing about their launcher beyond config discovery (`hooks/pretool-host-backup.ts:137-194`). An isolated executor session would today be captured like any other session unless its session id matched an ignore pattern — the queue-side marker plus a boundary rule are both needed.

## 10. Risks and open questions (priority order)

1. **Batched questions vs one-item-per-subject.** The decide pass batches up to 10 records per request and shares one state read across them, and treats the whole request as each answer's input (`decide-route.ts:190-197`, `decide-items.ts:194-198`, `decide-items.ts:120-125`). Queue items are per-subject with one input hash (`records.ts:116-127`). Either the executor loses batching (cost, ordering by `occurrence`), or an item must carry several subjects — which changes `answer` (one answer record per item) and the supersede rule. Unresolved in the design.
2. **Thresholds have no home in the queue.** Today a closed answer acts only above a per-model threshold (`use-thresholds.ts`; e.g. `decide-route.ts:189,210`). `answerWork` validates shape only (`queue.ts:583-591`). If the launched agent answers closed questions, either the threshold moves into `validate`/`apply` per operation or the queue accepts un-thresholded answers — a behaviour change the current tests pin against.
3. **The `rollup-summary` apply must become real text writing with a draft state that does not exist.** `applyAccepted` runs every pass and collects the throw (`queue.ts:633-644`, `pass.ts:51-64`); the first executor turns that into writing a note whose "apply drafts automatically" is a setting (brainstorm §Model work 8) — the draft record kind, its author field and the setting key are all undefined (`verdict-writes.ts` shows `authority: "model"` as the only precedent).
4. **Isolation has no marker and no profile.** The design requires "its own startup hooks and capture suppressed before initialization" and "a marker in its environment prevents recursion but grants nothing" (`brainstorm.md:91`); no suppressor marker exists (§7) and the profile mechanism retains the capability diagnostic and cannot yet express "three tools only" (`profiles.ts:12-15`). An adapter that cannot enforce isolation "is treated like an agent with no command-line mode" — no such classification exists in `RUNTIME_FACTS` (`host-facts.ts:503-677`).
5. **Per-run credential is a new token kind.** The token store mints per-agent, long-lived credentials (`token-store.ts:182-212`); the design wants "a credential scoped to the run" (`brainstorm.md:91`). Minting a per-pass token per pass multiplies records; not minting one means the executor shares the owner agent's identity. Needs a decision, plus a decision whether the executor rides HTTP (token, `http.ts:515`) or stdio (config identity, `token-cli.ts:47-52`).
6. **No non-interactive invocation forms are recorded for any host.** First setup must verify the launch command with a real short call (`brainstorm.md:96`), but the repo records only `mcp list`/`mcp add` forms (`host-facts.ts:539-545`); the fallback list ("filled in for known agents") has no source data — every preset line would be new, untested knowledge.
7. **The owner gate and the executor's writes.** `answerWork` refuses a lease granted by a previous owner (`queue.ts:574-576`) and the fold rejects any record not written by the current owner's device (`fold.ts:189-191`); a long drain across an owner transfer silently strands in-flight answers. The design covers the lease generation but not the user-visible reporting of stranded answers (only `dream-queue-rejected` counts them, `queue.ts:819-820`).
8. **Budget and backlog interaction.** The pass's 20 s decide budget (`decide-shared.ts:33`) disappears when questions are queued; what bounds the *worker's* per-pass item budget ("a pass has a budget of items, time and tokens", `brainstorm.md:92`) is unimplemented — `applyAccepted` and `takeWork` are unbounded (`queue.ts:621-648,466-476`), and the backlog threshold only reports (`constants.ts:62-63`).
9. **Private work visibility for the executor.** An item lands in `private` when any source is private (`queue.ts:396-398`); a device that lost `private` reports it unknown (`queue.ts:831-838`). The executor session must be able to *read* private evidence to answer — i.e. it must run at local reach and hold `private`, which conflicts with a minimal, credential-scoped surface unless explicitly designed (the `withholdPrivate` lever exists at `queue.ts:754-766`).
10. **Ordered work behind a stuck item.** Readiness already blocks on `after` and shared `resources` (`fold.ts:370-394`), and model work that depends on a parked item waits — but the rollup identity rung's `after` is produced from item ids (`rollup-work.ts:122-131`), so a parked fact-rung item parks the whole ladder chain by construction; doctor names only the parked item (`status-view.ts:54-58`), not the fan-out of what waits behind it. Reporting that fan-out is new surface work.
