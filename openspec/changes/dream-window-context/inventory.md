## 1. The dream pass as it is

`dream()` is a wrapper that orders three pieces: `withLogReadPass(() => dreamRun(...))` inside `withTopicPass` inside `withViewPass` (`src/core/brain/dream.ts:234-263`). Live callers per `openspec/changes/agent-neutral-dream/design.md:5`: the CLI verb `src/cli/brain/verbs/dream.ts:563`, the MCP tool `src/mcp/brain/dream-tools.ts:397-406`, the staged apply `src/core/brain/dream-stage.ts`, the heal-enrich step `src/core/brain/dream-step.ts`, the maintenance lane's dream task `src/core/brain/maintenance/lane-tasks.ts:124-130`. Preview-only callers: `src/core/brain/review-candidates.ts`, `src/cli/brain/verbs/summary.ts`, `src/mcp/brain/brief-view-tools.ts`.

Ordered steps of `dreamRun` (`src/core/brain/dream.ts:320-699`):

1. **Setup / repair.** `loadBrainConfig` (dream.ts:337); `repairLaneEntryIds(vault)` on non-dry store paths (dream.ts:341-347, `src/core/store-migration/lane-id-repair.ts`) — moves lane entries filed under another path's id; no-op once repaired. Warning collection from `primary_agent` mismatch (dream.ts:361-364; `dream-outcome.ts:72-85`). Reads `_brain.yaml`/store settings; writes lane records. Idempotent: yes ("never a reason to fail the pass", retried next pass).
2. **Scan.** `scanBrain` (`src/core/brain/dream-scan.ts:285-361`) reads the whole `Brain/` tree: `inbox/`, `processed/`, `archived/` (as `SignalRecord`s), `preferences/`, `retired/`; on a store-only machine the pages are rebuilt from the store's folds (`storeMemoryPages`, dream-scan.ts:119-126; `src/core/brain/memory-pages.ts`). Tombstoned signals/preferences skipped (dream-scan.ts:164-165, 194-197). Writes nothing. Idempotent: yes (pure read).
3. **Intent review.** `buildIntentReview(vault, { now, readable })` (dream.ts:384-387, `src/core/brain/intent-review.ts:57-105`): read-only clustering of active signals within the contradiction window; unexpired, in-window only (`intent-review.ts:69-70`); `generated_at` stamped from `now`. Writes nothing.
4. **Topic plan.** `planTopics(scan, cfg, now)` (`src/core/brain/dream-plan-topics.ts:62-159`): expires lapsed signals (`dropExpiredSignals`, 174-179), groups by folded topic key (`topicKey`, `dream-plan.ts:54-56`), decides promote / note-redundant / rebuttal / suppress / quarantine / contradiction. Pure; writes nothing. Idempotent: yes.
5. **Signal archive plan.** `planSignalArchive` (`src/core/brain/signal-archive.ts:131-164`): inbox signals outside the window are planned to `inbox/archived/`. Pure; apply moves files. Idempotent: yes (collision-safe, `archivedNames` check).
6. **Evidence scan.** `scanApplyEvidence(vault, checkpoint)` (`src/core/brain/dream-refresh.ts:146-214`): reads the entire operational log — day files under `Brain/log/` on an unswitched machine, the whole `log-event` stream on a store-only one — via `logDayReader` (`src/core/brain/log-days.ts:208-272`), keeping `apply-evidence`, `merge` events (`EVIDENCE_LOG_EVENTS`, `src/core/brain/evidence.ts`). Sorted by wall-clock timestamp ascending (dream-refresh.ts:212). Writes nothing.
7. **Refresh plan.** `planRefresh` (dream-refresh.ts:244-532): per preference, counters, unconfirmed→confirmed promotion, quarantine transitions, confidence (`computeConfidence`, `src/core/brain/confidence.ts:38-78`), outcome-regression penalty, freshness trend. Writes nothing.
8. **Retire plan.** `planAutoRetires` (`src/core/brain/dream-plan-retires.ts:33-98`): expired-unconfirmed, stale-no-evidence (normal and chain-decay windows). Pure.
9. **Cross-topic plan.** `resolveCrossTopicConfig` + `planCrossTopicRules` (dream.ts:433-443; `dream-plan-cross-topic.ts:306-367`): reads the persisted ledger `readCrossTopicLedger` (202-214). Writes ledger only at apply-time report stage.
10. **Reconcile.** `buildReconcileOutcomes` (`src/core/brain/reconcile-outcomes.ts`, dream.ts:456): contradiction domain classification, auto-resolve by source-freshness gap. In-memory only.
11. **Salience gate.** `applySalienceGate` (dream.ts:464, `src/core/brain/salience-gate.ts:326-333`): off unless `dream.salience_threshold` set; reads lessons/observed-use.
12. **Rollup ladder plan.** `buildRollupPlan` (dream.ts:480, `dream-rollup.ts:17-31`; `rollup-ladder.ts:174-222`): reads `readRollupLedger`; plan before the `changed` gate; ledger written only when fired (dream-report.ts:186-188).
13. **`changed` gate.** `hasStateChange` (dream.ts:482); no-op path regenerates digests and returns `buildNoOpSummary` (dream.ts:483-499). On the no-op path the pass still writes the derived digest pages (see step 17) — so a rerun that plans nothing is *not* strictly byte-idempotent on disk, only on the plan.
14. **Snapshot + apply.** `withDestructiveSnapshot` (dream.ts:575-598, `src/core/brain/snapshot-gate.ts`) takes `Brain/.snapshots/<run_id>.tar.zst`, then `applyDreamPlan` (`src/core/brain/dream-apply.ts`): writes new preferences via `writePreferenceTxn` `overwrite: false` (dream-apply.ts:206-236), cross-topic promotions (238-270), refresh updates, moves to `retired/`, moves consumed signals `inbox/`→`processed/`, archives unconsumed expired-window signals `inbox/`→`inbox/archived/`. No vault: no snapshot, direct apply (dream.ts:562-573). Idempotency: a second run on the same input plans nothing (evidence already folded into counters; signals already in `processed/`), and the workrun/`changed` gate make a partial rerun safe; preference writes are `overwrite: false` so a half-completed state surfaces as an error or a `skip`, not a duplicate.
15. **Audit log.** `writeDreamLog` (dream.ts:620-636, `src/core/brain/dream-report.ts:100-200`): appends `dream`, `retire`, `reconcile`, `signal-suppressed` events to `Brain/log/<isoDate(now)>.md` (dream.ts:672-675) or `log-event` store records on a store-only machine; writes the rollup and cross-topic ledgers when fired (dream-report.ts:186-199). Appending the same events twice would double them — protection is that a rerun plans nothing, not that the append is idempotent.
16. **Digest regeneration.** `regenerateDigestPages(vault, now)` (dream.ts:315-318, 643; no-op path 483): `regenerateActiveQuiet` / `regenerateLessonsQuiet` — `Brain/active.md`, `Brain/lessons.md` or the device-local cache (`src/core/brain/compiled-digest-path.ts`). Rewritten every pass even when nothing else changed.
17. **Workrun finalize** (dream.ts:520, 660, `dream-workrun.ts`).
18. **Topic step** `withTopicPass` (dream-tail.ts:31-89) → `runAutoTopicPlanning` (`src/core/topics/planning.ts`): store topic planning on the view writer only; writes topic/route/verdict records.
19. **View step** `withViewPass` (dream-tail.ts:99-128) → `runAutoViewPass` (`src/core/view/auto-render.ts`): renders human view pages on the view writer, budget `VIEW_DREAM_BUDGET_MS` (`src/core/view/constants.ts`).

## 4. Ordering and addressing in the brain store

- **Per-shard byte offsets are the one stable read position.** `readShard`/`scanShard` (`src/core/store/reader.ts:343-522`) read a shard from a byte `offset` and return `nextOffset` ("First byte not consumed: where the next read of this shard resumes", reader.ts:114-115); an incomplete or unverified last line is held back (`pendingTailBytes`, reader.ts:117) and retried, never skipped. A shard is per-device (`<stream>/<device>/<YYYY-MM>[.<suffix>].jsonl`, `src/core/store/shard-list.ts:6-8`), so a position per source is naturally `(device, shard rel, byte offset)` — the reader already returns the device (`shardDeviceOf`, reader.ts:208-212) and `listShards` returns shard entries sorted by partition-relative path in code-unit order (`shard-list.ts:84`), and `readStreamRecords` walks them in that order (`stream-read.ts:462-506`).
- **Stream-level facades** under `src/core/store/read/`: `readStreamRecords` (`stream-read.ts:433-529`) with optional `device` and `month` filters and in-process `ShardTails` (append-only incremental re-read, `stream-read.ts:142-179` — process-lifetime only, not a durable position); `readStoreLogEvents` (`src/core/store/read/log-events.ts`); record facades `signals.ts`, `preferences.ts`, `store-entities.ts`.
- **Late-synced record from another device**: it lands in that *device's own shard* (the reader refuses a record whose `device` is not its shard's directory, reader.ts:264-267), which may be a new file or a new month. Two cases: (a) an append to a shard already read — it appears after the previously read records of that shard, and `nextOffset`-style resumption sees it; (b) a new shard — `trackSeenShards` records it as fresh (`seen-shards.ts:451`), the listing reports it, and the next whole read picks it up. Either way the record's **envelope order position is stable and append-ordered per device**; what moves is when this machine first sees it.
- **What cannot be used as a position**: the `hlc` ordering (`compareRecords`, `src/core/store/envelope.ts:243-249` = hlc, then device, then id) is causal *at write time*, but a record that syncs late carries an **earlier** HLC than records already read — an HLC watermark silently skips it (this is exactly why `withLogReadPass`'s cache key is shard size/mtime, `log-days.ts:91-107`, not a clock). Record `created_at` / log `timestamp` are wall-clock strings of whichever device wrote them; the decide pass already defends only against *future*-dated records (`decide-shared.ts:48-51,71-77`) and otherwise sorts by them (`dream-refresh.ts:212`). Day-file grouping (`groupByDay`, `log-days.ts:174-187`) keys on the timestamp's date, so a late-synced event appears under its original day — a date cursor would neither skip it correctly nor replay it in causal order.
- **Compaction** invalidates per-shard offsets: a `compacted` record names `replaces`/`into` shard sets (`reader.ts:103-108,142-146`), `replacedShards`/`classifyMissingShard` (`reader.ts:566-578`) tell a caller whether a gone shard was compacted away; a durable position must rebase on compaction, like `ShardTails` does by deleting the entry (`stream-read.ts:507-511`).
- **A correct "position per source" can be built from**: the `(device, shard rel)` listing plus each shard's `nextOffset` and the gap predicates (`shardReadGap`/`shardScanGap`, `reader.ts:533-543` — pending blobs and non-torn corrupt lines make a read incomplete, so coverage may not advance past a gapped shard), together with the seen-shards ledger as its durable per-machine home and compaction records for rebasing.

## 5. Fixed-rule judgments a decision model may replace

- **Obligations / pledges** (`src/core/brain/obligations.ts:1-19`, `src/core/brain/pledges.ts:1-31`): durable Markdown pages with due dates and fulfill/archive semantics — an operator-facing queue precedent, not a machine queue.

## 9. Risks and open questions for the design, in priority order

1. **Archive is a one-way door ahead of the replay.** Step 3 of a pass back from silence archives everything outside the window before any replayed judgment can run (`signal-archive.ts:44-49,109-124`); the plan-side filter has already dropped the same signals (`dream-plan-topics.ts:174-179`). The queue change must either freeze an input boundary before the archive rule (brainstorm item "an initial boundary… frozen", `brainstorm.md:82`) or make archive replay-aware — otherwise "no gap" is unachievable regardless of positions.
2. **The evidence walk has no position.** `scanApplyEvidence` reads the whole log and sorts by wall-clock timestamps (`dream-refresh.ts:146-214`); coverage "advances only after outcomes are durable" has nothing to advance *from* — a per-source `(device, shard, nextOffset)` cursor exists in the reader (`reader.ts:114-115`) but no durable form of it does (§3, §4).
3. **Timestamp ordering is not causal across devices.** Both the evidence sort (`dream-refresh.ts:212`) and day grouping (`log-days.ts:174-187`) key on wall-clock strings; a late-synced record reorders the past. HLC cannot be the watermark either (§4). The design must say which order replay follows and what "reconciles records that synced late" means for an already-advanced boundary.
4. **The decide pass's asked-set and 8-week window will silently eat a backlog.** Newest-first caps + 20 s budget + 8-week lookback mean items unanswered during the silence are progressively lost (`decide-shared.ts:33,42,52-63`), and the deterministic rule decides them anyway — the exact "rule stands in for the model" the 2.0 design forbids (`brainstorm.md:87`, "Rejected" 6). Whether the decide pass migrates onto the durable queue or is replaced by it is undecided in `proposal.md` (the queue is change 2; executors are change 3).
5. **Ordered work must not overtake a stuck head** (`brainstorm.md:93`): the only existing ordering primitive is per-shard append order; queue items referencing a record chain or topic need an explicit ordering key, and the rollup ladder's baseline-reset behavior (one envelope for any backlog size, `rollup-ladder.ts:189-211`) shows what happens without one.
6. **Two durable ledgers already live in vault-synced files with per-day semantics.** `cross-topic-rules.json`'s daily budget (#8) and `rollup-ladder.json`'s counters are vault files (`paths.ts:137-144`) written by whichever machine runs the pass; with an owner gate this is fine, but a replay that reprocesses old windows needs to decide whether per-day budgets are judged against the replayed day or the run day (`dream-plan-cross-topic.ts:309`).
7. **Cross-machine lease semantics.** The maintenance lease is device-local SQLite and the known two-holder failure is recorded (`brainstorm.md:33`); the queue's leases must follow the view-writer fold pattern (§6) rather than the SQLite lease, and answer `take/answer/finish` (`brainstorm.md:90`) needs its stale-lease recovery rule defined — expiry exists only in the SQLite pattern today.
8. **Idempotency of the audit tail.** Log append and digest regeneration are not idempotent writes; they are safe only because a rerun plans nothing (§1 steps 13-16). A replay that processes multiple windows in one run will append one `dream` event per run — the digest "covers the interval that was really processed" (`brainstorm.md:80`) has no field to carry that interval today (`buildSummaryBody`, `dream-report.ts:171-183`).
9. **The gap predicates must gate coverage.** `shardReadGap`/`shardScanGap` (`reader.ts:533-543`) and `unreadable` shards (`stream-read.ts:48-54`) are the difference between "empty" and "unknown"; a coverage cursor that advances past a gapped shard reproduces the fail-open bug the store's design forbids. The decide pass already returns empty on `unreadable` (`decide.ts:87`).
10. **Compaction rebasing.** Any durable per-shard offset must handle `compacted` records (`reader.ts:103-108,566-578`); the only existing consumer pattern is `ShardTails` deleting stale entries (`stream-read.ts:507-511`), which is in-process and never durable — an open design point with no precedent to copy.
