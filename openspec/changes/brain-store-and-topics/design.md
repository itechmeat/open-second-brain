# Design

## Context

See proposal.md for the motivation and brainstorm.md for the chosen approach. Facts from the code and a live install (2026-11-06) that shape the design:

- **Catalogue.** `src/core/state/surfaces.ts` (`STATE_SURFACES`, about 60 rows) already lists every state location the product keeps in the vault, with its tier and reason. It is the migration manifest.
- **Sharding.** `src/core/brain/ledger-shards.ts` already shards append-only ledgers per device (`<base>.<deviceId>.jsonl`) and merges them on read in order (key, shard id, line). The new store generalises this pattern.
- **Device id.** It lives in device-local config and is never synced (`src/core/config.ts`). Nothing that every machine must agree on can live there.
- **Writes today.**
  - Signals are one Markdown file each (6.6k live).
  - The log append (`log.ts`) takes a directory lock, re-reads the whole day file and rewrites it atomically for every event, about 5k events a day per device.
  - `pinned.md` is written read-modify-write with no lock.
  - Preferences are Markdown files under per-file locks.
- **Index.** `brain.sqlite` can already be relocated (`search_db_path`). It holds vault-relative paths, and 6,655 of its 7,928 documents are signals.
- **Defects the move must fix rather than carry over:**
  - `.state/anticipatory/` is never pruned (3,647 files, 305 MB).
  - Upgrade snapshots bypass retention (911 files, 1.7 GB).
  - The dream pass has not run on the live install since 2026-05-24, which is why 6.6k signals sit unprocessed.
- **Vault assumptions.** Obsidian is required only by `.base` files and by wikilinks used as record identifiers. Note tools (`brain_create_note` and related) already refuse `Brain/` paths.
- **Outside readers.** Skills (`skills/brain-memory`, `skills/open-second-brain` and the `plugins/codex` mirrors), the MCP instruction segments, hook messages and the MCP resources `osb://log/{date}`, `osb://preference/{id}` and `osb://topic/{slug}` hard-code `Brain/` paths or the old meaning of "topic". The Python Hermes shim delegates to the CLI and needs no path logic.

## Goals / Non-Goals

**Goals:**

- No Open Second Brain machine file in the vault after migration.
- One store folder (two with the `private` partition) for the user to sync.
- Same folded state on every machine.
- Reads that see a neighbour's record as soon as file sync delivers it.
- Context injection bounded by budgets.
- A brain that works with no vault at all.

**Non-Goals:**

- A server, relay or real-time channel.
- Encryption at rest. It is documented as the sync or disk layer's job.
- Changing the CLI or MCP tool contracts beyond new verbs and new optional fields.
- Rewriting in Rust. Formats must simply be easy to port.
- Changing how user notes are written.
- Multi-user brains: one user, several machines.

## Decisions

### D1. Store layout

```
<store>/
  FORMAT.md                         format document (versioned, shipped)
  shared/                           partition, synced to every working machine
    events/<device>/<YYYY-MM>.jsonl     signals, evidence, notes, feedback
    log/<device>/<YYYY-MM>.jsonl        operational log, lifecycle, continuity
    ledgers/<name>/<device>/<YYYY-MM>.jsonl   idempotency, audit, metrics, receipts, lineage
    topics/<device>/<YYYY-MM>.jsonl     topic events
    settings/<device>/<YYYY-MM>.jsonl   shared settings (view writer, thresholds, migration records)
    digests/<device>/<YYYY-MM>.jsonl    state digests
    blobs/<sha256[0:2]>/<sha256>        large bodies, immutable
  private/                          same shape, for private-visibility records
                                    shared/ and private/ are synced as separate folders;
                                    the store root itself is never a sync folder
<device-local state dir>/           never synced: index, locks, caches, hook state,
                                    snapshots, maintenance lease, freshen state
```

The device-local directory comes from the platform data directory (`src/core/platform-dirs.ts`), keyed by store id.

Alternatives:
- One shard per writer process, as the author first proposed. Rejected: process ids churn, so the shard count grows without bound.
- One shard per device per day. Rejected: about 30 times more files than monthly shards, with no gain.

### D2. Appends

A record is one JSON line written with a single append (`O_APPEND`) call, under a device-local advisory lock on the shard. The lock is held only for the write and is never synced. Lines stay under a size cap; larger bodies go to `blobs/`. This replaces the full-file rewrite in `log.ts`.

On Windows the append opens with `FILE_APPEND_DATA` inside the same local lock.

Alternative: lock-free `O_APPEND`. Rejected because Windows append atomicity is not guaranteed for every size, and the local lock is cheap.

### D3. Envelope and clock

Every record has this shape:

```
{ "v": 1, "id": <ulid>, "hlc": "<physical_ms>.<counter>", "device": <id>,
  "agent": <name>, "kind": <kind>, "scope": <scope>, "topic": <topic id|null>,
  "sum": <sha256 of body>, "body": { ... } }
```

- **Fold order** is (hlc, device, id).
- **Clock rules.** Standard HLC.
  - Send: the physical part is the larger of the wall clock and the local clock; the counter increments on a tie.
  - Receive: every catch-up raises the local clock to the largest clock it ingested.
  - So a record written in reply to a remote record always folds after it, even when the replying machine's wall clock is behind. Skew of seconds is harmless at sync latency.
  - As built (phase 2): reading is receiving. Every shard read raises an in-process floor for its store, and the next stamp for that store takes the receive rule over the floor first, so a write that replaces, removes or raises a record the operation read (a replacement, a tombstone, a privacy raise) folds after that record even when its device stamped it minutes ahead of this machine's wall clock. A stamp more than a day ahead is still not adopted.
- **Readers** skip an incomplete or checksum-failing last line and retry it on the next pass. A failing middle line is reported by doctor.
- **Unknown `v`:** the record is skipped and doctor reports it.

### D4. Folds of mutable entities

Preferences, pinned context, topic fields, assignments and settings are folds over records with precedence human > agent > decision model, then the later clock wins within an authority. Removal is a tombstone record.

- Preference counters (applied, violated) are derived in the fold, not written back. This removes the stale-counter class of bugs.
- The existing preference audit trail (`pref-audit.ts`) becomes these records.

### D5. Index

`brain.sqlite` moves to device-local state and gains three things:
1. A watermark table per shard: path, file identity (inode or Windows file id), size, mtime, byte offset and a hash of the verified prefix. A changed identity, a size below the offset, or a prefix hash mismatch resets that shard to offset 0. The re-read is idempotent by record id.
2. A `records` table (id, stream, kind, scope, topic, hlc, device, agent) beside the existing documents and chunks.
3. A source column that separates brain records from user notes.

Catch-up runs before reads: stat each shard, then read only from the stored offset. Stats are throttled to once per second per process, and a directory listing is cached by directory mtime. The phase 1 benchmark (500 shards, nothing changed) must stay under 20 ms. The change probe ("what is new since W") is an index query, not a file read.

A full rebuild uses the existing `brain.sqlite.new` and swap path.

### D6. State digests

Digests are computed per partition over an explicit cut. A cut is a vector of (shard, record count, last record id) for every shard the machine holds in that partition, excluding the `digests` stream itself, so publishing a digest never changes the cut being compared.

After catch-up, a machine writes a digest record carrying the cut and a hash of each fold computed from exactly those records. Doctor compares only digests whose cuts are identical, so idle devices, offline devices and machines without a partition never produce a false alarm or a stall.

Roster: the devices with records in the partition during the last 30 days, minus devices retired by a `device-retire` human record. Doctor reports a roster device that has published no digest for 7 days.

### D7. Human view: one configured writer

**One writer.** The human view and topic-creating dream steps have exactly one writer device, the *view writer*. It is named by a `view-writer` human settings record in the `shared` partition, so every machine agrees on it.

- The first machine that migrates or initialises the store records itself as the view writer.
- `o2b view writer --here` moves the role in two steps:
  1. It records a `view-writer-request`.
  2. The current writer sees it at its next catch-up, finishes any render in progress, and records `view-writer-released`.
  3. The new device renders only after it has caught up on that release record.
- `--force` skips the release when the old writer is unreachable, with a warning that a still-running old writer may write pages once more before it catches up. The old writer always catches up before rendering, so it stops at its first render after the change reaches it.
- When two machines initialise a store at the same time, the claim with the lowest (clock, device) wins once both claims sync. The loser has written no pages, because a fresh writer waits one full catch-up after its claim before its first render.
- Another device never writes view pages, even when the writer is offline. Pages then go stale, but no data is lost.
- Doctor on every machine reports a view writer that has published nothing for 3 days, and names the command to move the role.

Alternative: an expiring lease that passes the role on automatically, as the partner first proposed. Rejected by the review: delayed file sync cannot make a lease exclusive, so two holders could render different record sets into conflicting copies of one page.

**Render protocol on the writer:**

1. Catch up.
2. For every page, compare the file on disk with the checksum in the last render record.
3. A mismatch is a human edit. Three-way merge it with the base (the last rendered text, kept as a blob referenced from the render record), the file on disk and the new render. Store the user's changes as human records before rendering.
4. Render to a temporary file and check the page checksum once more right before the rename; if it changed, go back to step 3.
5. Write a render record (page, checksum, base blob).

**No silent loss.** A phone edit that lands between the last check and the rename could be overwritten, and not every sync tool makes a conflict copy. To keep that edit recoverable:
- Before every rename the writer stores the on-disk bytes it replaces as a blob, kept for 30 days.
- After the rename it re-reads the page. If the replaced bytes differed from the base, it ingests them as a human edit and renders again.
- A sync-conflict copy of a page, when the tool makes one, is ingested the same way and then removed.
- `o2b view recover <page>` lists the replaced versions.

Promise to users: an edit is never silently lost. An edit that races a render may arrive one render later.

**Pages.** `about-me.md` (the profile page), `history/<YYYY>-W<ww>.md`, `decisions.md`, `reports/<slug>.md`, `sources/<slug>.md` and `topics/<date>-<slug>/topic.md`.
- Each page has one HTML comment line with its store id.
- There is no frontmatter and there are no Obsidian-only links.
- Generated prose uses `view.language` (a shared setting); quoted text stays in its original language.

### D8. Topics

A topic is a record family with an immutable `topic_id` (ULID). Topic events:

- `topic-create`, `topic-rename`, `topic-status`, `topic-goal`
- `decision`, `open-question`, `question-resolved`
- `log-entry`, `milestone`, `milestone-done`
- `assign`, `unassign`, `merge`, `split`, `link`, `undo`

Page schema: title, one-line description, status, goal, milestones, decisions, open questions, log (newest first), related. Decisions use one plain list with "serves" links where they help. The office prior art's four groups (Need, Surface, Internals, Method) are left out of version 1 because they fit engineering topics but not personal matters.

Code naming:
- The new entity owns `topic` in code, the CLI and MCP.
- The existing preference slug becomes `ruleTopic` / `rule_topic` in code; the persisted `topic` field on signals keeps its name for compatibility and is read as `rule_topic`.
- The resource `osb://topic/{slug}` becomes `osb://rule-topic/{slug}`. The old name is kept as an alias for one minor version, and the new `osb://topic/{id}` serves topics.

### D9. Automatic and requested topic actions

Only the view writer runs the topic-planning step of dream, under a device-local exclusive lock, so neither two machines nor two processes on the writer create the same topic twice. Dream assigns unassigned events to topics and creates a topic when at least N related unassigned events (default 5) from at least two sessions fall in one scope. Assigns and creates apply at once; each is listed in the dream report and can be undone with one command. Merges and splits are only proposed, in briefs and the digest, until the user confirms.

A topic created by request on another machine gets a fresh id there. If the planner later sees a near-identical topic, it proposes a merge (`topic_same`) and never merges silently.

Requested actions come through MCP tools (`brain_topic`, with actions create, assign, rename, status, merge, split, archive, undo) and the matching CLI verbs. A CLI verb is recorded as a human record (the user runs it), except `o2b topic record`, which writes an agent record unless `--as-human`. `brain_topic` writes agent records unless the caller names `human` on the user's explicit request, which is refused below local reach (D18 item 5).

### D10. Decision-model uses

All uses plug into `src/core/decision-model/` with modes `off`, `shadow` and `enforce`; every use is off by default.

| Use | Question | Deterministic fallback | Where it runs |
|---|---|---|---|
| `topic_route` | which active topic, or none | scope match plus lexical similarity over topic heads | writer, at record time |
| `event_kind` | decision, open question, log-worthy or routine | the kind the agent passed; otherwise routine | writer |
| `human_readable` | belongs in history or not | only records the agent flagged significant | renderer |
| `topic_new` | does this cluster deserve its own topic | count and session threshold | dream |
| `topic_same` | are two topics one topic | none (no proposal) | dream, reuses `pair-verdict` |
| `question_resolved` | does this record answer q{n}, and which one | none | dream |
| `milestone_done` | does the milestone look done | none | dream (proposal only) |
| `head_select` | which topic heads to inject | recency and scope ranking | session start (reuses `recall_inject`) |
| `neighbour_relevant` | does a neighbour's record matter to this task | same topic id and kind decision | before a turn |

- **Verdicts stored once.** A verdict is stored in the record it decides, with model id, version, mode and confidence. Folds read the stored verdict and never call a model, so machines converge.
- **Private data stays local.** Uses that read `private` records refuse a hosted provider unless the user opts in per use.

### D11. Migration

The command is `o2b brain migrate-store [--dry-run] [--resume] [--rollback]`. `o2b upgrade` offers it, and doctor and status report it. It never runs without consent.

Superseded in part by the change `auto-store-migration` (owner decision of 2026-11-17): after an update the product runs the migration on its own, in a background worker started at the session start and the MCP server start, and `o2b update` runs it in the foreground, unless the machine opted out with `auto_store_migration: false`; with the opt-out it is offered and never started, as described above (an automatic attempt that already started is still finished). The migration itself, everything below, is unchanged.

Order of work on the first machine:

1. **Preflight.** Config, free disk, no other migration running, store root outside the vault, and the device roster of the legacy tree. The roster is every device id found in legacy shard names during the last 30 days; the report lists them.
2. **Quiesce this machine** through a device-local migration gate, not the synced fleet freeze marker (`freeze-marker.ts` is shared across machines).
   - Every writer takes a shared lock on the gate file in the device-local directory for the length of each write.
   - The migration takes the exclusive lock. It waits until in-flight writes drain, then holds the lock to the end.
   - Writers that find the gate held refuse with a "migration in progress" message.
   - The phase 2 test runs several writer processes against one migration.
   - As built (phase 2): the gate is one device-local file, checked by the vault write guard every content writer passes, so a write that starts while the gate is held is refused. A write already past the guard when the gate closes is not waited for by a lock: a settle period after closing the gate lets it finish, the final delta pass imports what it left, and the transition import (D11a) picks up anything that lands later. No per-write shared lock is taken.
3. **Back up.**
   - Take a snapshot of `Brain/` through the existing snapshot path.
   - Make an explicit backup of every non-rebuildable `.open-second-brain/` surface. `STATE_SURFACES` marks secrets, keys, attestations, ingest and import checkpoints and lockfiles; the snapshot path excludes them today (`path-constants.ts:188`).
   - Each backup is verified by a restore into a temporary directory.
4. **Map.** Walk `STATE_SURFACES`. Each surface maps to a stream, a blob, device-local state, or "drop" (derived caches only). An unmapped surface fails the dry run.
5. **Convert.**
   - Signals become `events` records, using their original `created_at` as the clock's physical part.
   - Log JSONL lines keep their hash chain inside the body.
   - Preferences become seed records plus their audit history.
   - The journal is per item, and per line for append-only files: (device, source path, line or item, checksum, record id). Matching uses the whole key, never the checksum alone, so two distinct legacy records with identical content stay two records.
6. **Final delta pass.** Re-scan every source and import whatever changed or grew since its journal row. Repeat until a pass imports nothing.
7. **Verify** every journal row against the store.
8. **Render the minimal human view** (see D13 phase 2).
9. **Switch.** Record `migration-done` in the shared partition, carrying the per-partition cut of what was imported. Lift the freeze; writers now use the store only.
10. **Leave the legacy tree in place**, read-only to this machine, until every roster device has switched (D11a).

**D11a. Mixed versions.**
- **Upgraded machines import late writes.** A machine still on the old release keeps writing into the legacy tree, and sync delivers those files to upgraded machines. Upgraded machines import them line by line through the journal: new or grown lines only.
- **When the legacy tree leaves the vault.** At preflight the first machine records a durable *migration cohort*: every device id found anywhere in the legacy tree, with no age window. The tree leaves the vault only after every cohort device has written `migration-done` or `device-switched`, or has been retired by a human record, or the user passes `--force` (the report names the devices that will stop receiving data). A device that stays offline for months keeps the tree in place until one of these happens. Then the tree moves to a dated archive in the device-local state directory. It is never deleted automatically.
- **Until then** doctor on every machine lists the devices still on the legacy layout.
- Amended by the change `stale-device-retirement` (owner decision of 2026-11-19): a cohort device that has not switched counts as retired by silence once its last evidence of life (legacy shard name dates and row times, its store record clocks; never file modification times) is older than the shared setting `migration.silent_device_days` (default 30, 0 restores the cohort with no age limit), measured against the newest evidence of any device that is not later than this machine's clock (evidence stamped in the future is left out of that reference). The state is derived on every read, never recorded. The removal stays the user's command; doctor and the status block list each cohort device's state and say when the tree can leave; a device that comes back after the removal is handled as that change describes.

**Later machines.**
- A later machine waits until its catch-up holds every record of the `migration-done` cut for the partitions it holds, which protects against the record arriving before its data. A partition it does not hold is skipped and named in its report.
- It then runs the same pipeline over its own legacy files, because they may hold records the first machine never saw. The journal skips anything already in the store by checksum.
- It backs up and moves its own device-local surfaces, then writes `device-switched`.

**Rollback** (`--rollback`, per machine, until the legacy tree leaves the vault):
1. Freeze this machine.
2. Restore the snapshot and the explicit backups.
3. Replay into the legacy layout every store record whose stable identity (record id, or the legacy key for imported records) is absent from the restored tree. That includes remote records that arrived after the snapshot. Replay runs in fold order through legacy exporters for signals, log events, preferences, pinned context and notes, is idempotent, and can be resumed through its own journal.
4. Record kinds with no legacy form (topics, view renders, digests) stay in the store and are listed in the report.
5. Switch config back to the legacy layout and lift the freeze.
- As built (phase 2): a rollback is per migrated vault. The backup records the vault it was taken of (identity marker, else the real path), and a rollback for any other vault is refused before any file is touched. A vault a switched machine only imported through the transition (D11a) has no backup of its own and needs none: the transition never writes into its legacy tree. The transition binds such a vault only when nothing was held back and its operator settings, `_permissions.yaml` included, were imported without a conflict with the stored document.
- As built (phase 2): the same held-back rule gates the removal of the legacy tree (D11a). While the transition import holds an item back for a partition this machine does not hold, the removal refuses, names the count and the partition, and `--force` does not override it, because a rollback is refused once the tree has left the vault. A migration killed after its switch record is finished only for the vault it migrated (compared as a rollback compares it); a vault configured since stays unbound and goes through the transition's own checks.
- As built (phase 2): the journal keys every import by the vault it came from as well (identity marker, else the real path, compared as a rollback compares them; the store holds only a hash of the path), so an identical item at the same path of a second vault gets its own record. Rows and records written before carry no vault and count for the first vault this machine migrated, never for another. The migration, and the transition that binds a vault, record the automatic import's legacy-file watermark from the stamps taken before their final delta pass; with no watermark the automatic import runs and the journal decides what it still lacks.
- As built (phase 2): a dual-written copy stands in only for an item of the vault it was dual-written from. The content match leaves the vault out, so the pool checks it: a copy whose `vault_id` names a marker counts only for the vault with that marker, and a copy with none counts only on the device that wrote it, for the vault that device migrated. An identical item of another vault, or one whose unmarked copy another device wrote, gets a record of its own: a duplicate, never a merge.
- As built (phase 2): a path is device-local, so the migration (first and later machine) gives a vault without an identity marker its marker before it writes any journal mark, and the marker reaches the other machines by sync. A mark from another device proves a vault only by its marker id; a mark that names a path alone, or no vault, counts only on the device that wrote it and only for the vault at that path. A later machine whose vault has no marker, while another device's migration named its vault by one, waits for the marker to arrive instead of minting a second one; for a vault that is a different one, `o2b brain init` gives it its own. The transition on a switched machine writes nothing into a vault's legacy tree (item 1 of D14), so it creates no marker: a vault it imports without one gets path-only marks, and another device imports its own copy of those items rather than merge them with another vault's.
- As built (phase 2): a data path that ends in a step a later run cannot take back reads the store completely or not at all. While any held shard (the `digests` stream aside) is unreadable, gone since this machine read it, or read only in part, the rollback refuses before it touches anything and again before its restore, names the shards, and keeps the switch; the removal of the legacy tree refuses (a partial shard only without `--force`, as for a `settings` shard); the transition imports a vault configured after the switch but does not bind it and names the shards; and the migration refuses in its preflight and again before its switch steps, so the machine stays on the legacy layout.
- As built (phase 2): the rollback matches what the restored tree already holds per vault, by the journal's rule: a `migrated` mark counts as restored only when it names this vault, and a dual-written copy stamped with another vault's marker is never matched by content. Another vault's occurrence of an identical item is written back beside this vault's. A copy that names no vault keeps the content match, so a peer's dual write from before the marker is not written back twice.
- As built (phase 2): topic planning dates a record the migration imported by its legacy item, not by its envelope (the migration's clock and machine): the session fallback and the candidate time take the log event's `timestamp` or the signal's `created_at` (an ISO day or a zoned time), else the day in the legacy file name, else the clock, and the device of the legacy shard (`legacy_device`), else the envelope device. The imported record is unchanged, so its checksum, its journal identity and the rollback stay as they were; a single-agent history written over several days forms topics as it would have before the migration.

Doctor reports legacy directories that reappear after the tree left the vault, with the writer when known.

### D12. Path discovery

`o2b store path` (JSON: store root, partitions, device state dir, view target) and an MCP field in `second_brain_status` replace hard-coded paths. Skills are rewritten to name tools and commands only, and `plugins/codex` mirrors are regenerated with `bun run sync-plugin-mirrors`.

### D13. Phasing

The change ships in four releases, each one PR carrying its own version bump, CHANGELOG entry and docs:

1. **Store core:** layout, envelope, appends, folds, digests, index catch-up. Writes go to both the store and the legacy tree behind a flag that is off by default. The defect fixes (cache prune, snapshot retention, log append, pinned lock) ship here.
2. **Migration, the vault-free mode and the minimal human view:** the view writer, the render protocol and the pages `about-me.md`, `history/` and `decisions.md`, so the preferences that leave the vault have a readable replacement on the same day.
3. **Topics, plus reports and sources pages.**
4. **Decision-model uses and agent-context budgets.**

### D14. Store-only mode: answers the phase 2 inventory raised

The inventory for task 2.10 (316 modules reach the legacy tree) raised questions the decisions above did not settle. They are settled here so the work can split into parallel packages.

1. **Switch.** A machine is store-only once it holds its own `device-switched` record (D11, D11a); a fresh install with no legacy tree is store-only from the first write, and `o2b init` runs `o2b store init`. In store-only mode a store failure fails the operation with the reason and the remedy; nothing is skipped silently. Hooks and other fail-open paths log the failure to the device-local hook audit and continue.
   As built (phase 2): the switch is sticky per machine. The migration and the fresh-install switch record it in a device-local marker as they switch the device, and from then on the marker alone answers switched: a `settings` shard that is absent or unreadable while sync delivers it never sends the machine back into the legacy tree, and every check of whether this device switched (the migration's preflight, the rollback, the automatic import, the status block, doctor) reads the same marker. Only a rollback clears it. The removal of the legacy tree refuses while any `settings` shard of `shared` cannot be read, since a cohort record or a peer's switch in it would be missed.
2. **Record lanes with no record kind** (decisions, obligations, pledges, theses, tensions, gap tasks, attention flows, entities, procedures, procedural memory, skill proposals and benchmarks, captures, clusters, bridge proposals, triggers, handoffs, dead-ends, personas, write sessions, foresight, dream staging, architect projects, the profile page, report snapshots): one generic kind, `lane-entry`, with the lane name, a stable entry id, the structured fields the page carried in frontmatter and the Markdown body. Entries fold by id under D4. Their tools read the fold and work with no vault. Pages for people come from the view (phase 2 `decisions.md`, later phases for the rest), never from these records' old files.
3. **Settings.** Each `_brain.yaml` key is classified once: keys about one machine belong in device config; keys every machine must agree on become shared settings records (D1, `fold-settings`). Migration imports the changed shared keys of `_brain.yaml` as records and writes the changed device keys into the machine config as `<key>: <JSON value>` lines, never over a key the config already sets (the user's value stays), and reports what it wrote and what it kept, so a device key does not fall back to its default on the switched machine. A single reader returns the folded settings with defaults; the 39 readers call it. `_permissions.yaml` is a shared setting too: `permissions.document` holds its text, only the operator (human authority) sets it, the migration imports the file, and every gate reads the setting first and falls back to the file only on an unswitched machine where the setting is unset; doctor warns (`permissions-legacy-only`) when deny rules sit in a legacy file no gate reads.
4. **Standing rules** are human-authored: `lane-entry` records in lane `standing-rule` with authority `human`. A view page for them comes in a later phase; until then the CLI and MCP tools edit them.
5. **Signal lifecycle.** Moves between inbox folders become `signal-state` events (consumed, archived, retired, expired, staged, approved, rejected) keyed by signal id; the signal fold gives the current state.
6. **Backup-class surfaces** (secrets, signing keys, checkpoints, lockfiles) live in the device-local state after migration and are never synced; migration backs them up explicitly (D11). Attestation records are shared records; the keys that sign them stay device-local.
7. **Digests.** `active.md` and `lessons.md` are rendered on demand for hooks and MCP resources, with a cache in the device-local state. They are not view pages.
8. **Vault adapter.** One module, active only when a vault is configured, owns everything Obsidian-specific: `.base` files for user notes, wikilink audits and the note tools' vault requirement. No `.base` file queries store data; view pages carry no frontmatter for one to query.
9. **Snapshots** after migration cover the device-local state. The store needs none: shards are append-only with per-record sums and partition digests (D6). The migration snapshot (D11) covers the legacy tree until removal.
10. **Integrity.** Legacy day-file hash chains stay verifiable by the legacy reader. Store integrity is the record sums plus partition digests over cuts; there is no per-record chain.
11. **Derived ledgers** (rollup ladder, cross-topic) are device-local and recomputable; machines need not agree on them.
12. **Exports** (`export`, knowledge pack, OKF, bundle) read the folds and may keep the legacy layout as an interchange format. They are exporter modules for the 2.10 grep.
13. **Write guard.** In store-only mode the vault identity guard is replaced by the store identity check (store id and device id bound in the device-local state); the freeze marker is device-local and still holds every content write (lane pages, settings, schema applies), with or without a vault; a migration gate left naming the vault is a leftover of the migration that switched the machine and refuses nothing. Note tools keep the vault identity guard through the adapter.
14. **Vault filtering.** Store reads do not filter by `vault_id` (one brain across vaults, D1); `vault_id` stays as provenance. The search index lives in the store's device-local state, one per vault (keyed by a hash of the vault's real path), and is keyed by the store id when no vault is configured.
15. **MCP tokens** move from per-vault files to device config, so a server with no vault still enforces them; migration copies them. As built in 2.10 only the read side has moved: the transport reads `mcp-tokens.json` beside the machine config when it exists (with or without a vault) and otherwise the per-vault file (`src/mcp/token-source.ts`). The migration copies the per-vault file there (never over a device copy already present), and a rollback removes that copy again (or sets it aside when it changed since), so the per-vault file is the token map once more. On a switched machine minting, rotation and revocation write the device-config copy too (starting from the per-vault map when no copy exists yet), with the custody audit in the store, so a token minted after the switch authenticates with or without a vault.
16. **The 2.10 checks.** The test preload configures no vault; tests that need one create it. The grep is an architecture test with an allowlist and a reason per entry, covering the `Brain/` literal and `"Brain"` path segments in code, not comments; comments are updated by the package that owns the file.
17. **Note-tool walls** that refuse `Brain/` paths stay until the legacy tree is removed (D11a) and count as legacy modules.
18. **Privacy judge.** Once switched, reference privacy reads the preference and signal folds, not legacy pages; a reference the folds cannot resolve still counts as private (fail closed).
   As built (phase 2): a write that replaces an existing store-backed entry (a lane page or file, a tension transition, an entity merge or label prune, an exact-state aspect) keeps the strictest partition of the entry it replaces: an entry that lives in `private`, or whose fields reserve it, stays private whatever the new content says. No agent overwrite lowers a partition; an entry becomes shared only by removing it and writing it anew.
   As built (phase 2): a tombstone carries no content, so it goes to the partition of the entry it removes whatever the rest of its operation is, and no enclosing verdict raises it; this is the one exception to one partition per operation. A folder move or removal places each entry and its tombstone in that entry's own partition (a moved entry can still be raised, never lowered), so a device that holds only `shared` sees a shared entry leave a mixed folder. A write that raises a shared entry to `private` (a lane page or file, an exact-state aspect) writes the entry's shared tombstone first in the same store write, so a device that holds only `shared` sees the entry go and a device that holds both reads the private value.
   As built (phase 2): a store read whose answer decides a protection fails closed when it cannot see a shard it should consider. A shard counts as unseen when it cannot be read, or when this machine read it before and it is gone now: every stream listing records the shards it saw in a device-local ledger per store (`seen-shards-<root hash>.json`), and a shard the ledger names that the listing no longer finds is reported as unreadable, unless a `compacted` record replaced it or a human retired the device that wrote it. On an unseen shard a lane or exact-state write is judged private (refused on a machine without `private`), an exported lane entry counts as private, the capture boundary captures nothing, the permissions gates refuse, an agent settings write is refused (`settings_unreadable`), a signal removal refuses, the brain settings readers throw instead of answering defaults, and the decision ledger throws instead of answering "never gated". Doctor reports each unseen shard by its path (`store-shard-unreadable`). A shard read only in part counts as unseen too: one that holds a record whose body blob has not arrived, or a bad line in the middle (a checksum or envelope that does not verify, a record of a newer format). Its readable records are still read, and no fold cache keeps a read over an unseen shard, so the fold is read again once the blob arrives even though the shard did not change. Two cases are not gaps: the last line held back while an append is still arriving (the existing reading rule), and a line torn by a crash and closed by the next append, recognised as a JSON object cut short and never a record any machine read. The removal of the legacy tree refuses on a `settings` shard read only in part unless `--force`, since such a line may never read again; doctor's shard check does not report a partial read as an unreadable shard. On a machine the sticky marker names switched, a store that cannot be opened (`store.json` missing or corrupt) or that no longer shows its `shared` partition is unseen as a whole, never "no store, no rules": the permissions gates refuse, the brain settings readers throw and capture closes, an agent settings write is refused (`settings_unreadable`), lane and exact-state privacy is judged private, a signal removal refuses, and the decision ledger and the attestations refuse to read as empty. A machine that never switched still reads "no store" as nothing stored. The partitions a machine holds are sticky the same way: opening a store for writing and `o2b store init` record, in a device-local list per store root, every partition this machine holds, and a listed partition whose `store.json` is now missing makes the store unopenable by name. On every store-only machine (switched, or with no legacy tree) every protection reader then fails closed as for an unopenable store, so a private lane entry is never read as shared because its partition's identity file went away; every store write refuses, and doctor names the partition (`store-partition-lost`, an error). A machine that never held a partition (set up with `--partitions shared`) keeps working with the partitions it has. No command takes a partition off the list: the remedy is to restore its `store.json` from sync or a backup.

### D15. Phase 3 store follow-ups (tasks 3.9, 3.10, 3.11, 3.18, 3.21)

1. **Lane entry ids (3.9).** The path rule of `store/lane-paths.ts` is a bijection on the paths it accepts: a path names an entry only when that entry turns back into the same path, and every other name is refused with its reason. A page whose name without `.md` reads as a kept file (`x.json.md`) keeps its whole name, so it no longer takes the id of `x.json`. A user's top folder spelled otherwise than its lane name (`My Notes/`, `project_x/`: case, spaces, other separators) is not refused by the migration: its pages are imported under the normalized lane, with the original path in the `migrated` mark, which is where a rollback writes them back; two folders that take one lane are refused, both but the one spelled as the lane, and doctor names such folders before a migration (`lane-folder-unimportable`). Refused are a file with another extension or none, a top folder that is not a lane name or is the lane name of another folder (`exact-state`, `brain`), and the place of a root file with a lane. A store-only write of such a name refuses, and the migration lists it as an item it could not convert (archived with the other unparseable items) instead of filing it under an id that names another path. Refusal was chosen over an escaped encoding for these names: none of them is written by a writer of this tool, and an encoding would change the ids of entries already in stores. An earlier release did file a migrated page `x.json.md` under `x.json`: a store-only dream pass runs a repair (`store-migration/lane-id-repair.ts`) that moves such a record, recognised by the legacy path in its `migrated` mark, to the id its path maps to now, and gives the old id back the latest record that is not the page's (the file `x.json`), with at least the authority of the page record it replaces, or removes it. The page is written under its new id only when that id has no history at all, so a page removed after its repair stays removed. Every moved or restored record keeps the body it copies, its `migrated` mark included. The repair runs only on a machine that holds `private` (one without it cannot see a file's own record there and would remove the file's id over it), and once per store on a machine: a device-local marker records a finished pass that read every shard in full, with a stamp, taken before the read, of the `events` shards other devices write, so a later pass reads the stream again only once another machine's records arrived, a late import of a machine still on the earlier release included, and never for this machine's own writes. A pass that met an unreadable shard, one gone since it was read, or a pending blob writes nothing at all (it may have missed the file beside a page, or a removal) and runs again. The page's value and the old id's own value are each resolved as the register resolves them (authority, then fold order), never taken from the latest record. Each record lands in the partition of the record it copies; a file restored in `private` over a page that lives in `shared` also removes the page from `shared`, and a removal the move into an id replaces is kept when the move lands in another partition, so a machine that holds only one partition never keeps a stale page. The plan is written only once a read right before the write finds the same lane records, and made again from that read otherwise. The old id's own state counts its removals: a file removed before a page was filed over it stays removed. A page whose own id holds only a page filed there from the id after it (`x.json.md.md` under `x.json.md`) takes that id in the same pass, which moves the other page on. On a store where no machine holds `private` the repair never runs, so doctor reports mis-filed ids on every machine (`lane-id-misfiled`; it names only the repairs of pages the caller may read, below local reach only those no record of the `private` partition takes part in, with one remedy whatever the machine holds, and the legacy-folder check states its finding by name only, with no names or counts), naming them and the remedy: a dream pass on a machine that holds `private`, or adding the partition on one with `o2b store init --partitions shared,private` first. The old id's tombstone or restore is appended before the page's new record, and the rollback exporter writes an entry back to the legacy path of a `migrated` mark only when that path names the entry under the current rule (or names no entry the rule maps, a blob lane's file or a respelled folder), else to the entry's own path, so a rollback after a repair leaves both files at their own paths, and a lone page the snapshot restores is never removed by its old id's tombstone.
2. **Procedural counters (3.10).** The usage counters of procedural memory (`usage.jsonl`: uses, last use, successes, failures), the procedural graph and the recall hints are machine state, at their vault-relative paths on an unswitched machine and in the device-local state once switched, like the claim graph and the rollup ledger (D14 item 11). A use or an outcome rewrites only the usage file, so a usage tick appends no store record. Every read-modify-write of the usage file (a tick, an outcome, the reconcile that moves an index's counters into it) runs under the file's write lock and reads the file again inside it, so a reconcile in one process never drops a tick another process counted. A reconcile moves the counters an older index carries into the usage file before it rewrites the index without them, so a rebuild that fails afterwards leaves them in the usage file. A first adoption of the stored usage record is written under the same lock, only while the file is still absent. The index stays a shared `lane-entry` and is written with its counters at rest; a reader takes the counters from the usage file and falls back to those an older index still carries, and the next reconcile writes them into the usage file. The migration moves `usage.jsonl` into the device-local state (a `device-local` surface) and drops the graph and hints, which each machine recomputes. Counters are per machine from then on: they rank procedures for the machine that uses them, and machines need not agree on them. A machine switched before this change holds the three files as `lane-entry` records only: a reader with no machine-state copy yet reads that record and adopts it into the machine state on the first read, writing no store record, so the graph, the hints and the counters answer before the next reconcile. The records stay until the legacy tree leaves the vault, because a rollback replays post-switch records into the legacy tree and a tombstone would remove the legacy file they came from; the removal of the legacy tree, after which no rollback can run, adopts them on its own machine and then tombstones each one whose copy this machine now holds (`store-migration/retire-adopted.ts`); one it could not adopt (its device-local folder refused the write) or whose tombstone could not be written stays live, the one copy there is. A rollback before that loses only the counter ticks counted after the switch, which live in the device-local state; the legacy files come back from the snapshot. A machine that never read the records before their tombstone arrives rebuilds the graph and hints on its next reconcile and starts its counters from those its index carries.
3. **Schema apply attestation (3.11).** Of the two options, the audit row moves: a store-only apply writes it to `shared`, the partition of the `brain.schema.*` settings records it attests, so a machine that holds only `shared` finds the digest the pack must match and reports another device's apply as attested. The other option, accepting the newest settings records as attested, was rejected because it would accept any settings write to a schema field as an audited apply, which is exactly what the integrity check exists to tell apart. The `reason` does not belong on the shared row: it is free text an operator wrote, and audit rows have always stayed in `private` on a machine that holds it. So the shared row carries what attests the pack (actor, time, target, count, digest) and the mutation list, which the shared `brain.schema.*` records hold anyway, and the whole row, reason included, goes to `private` as every audit row does when this machine holds it; on a machine that does not, the shared row keeps the reason, the exposure such a machine always had. One privacy verdict covers the batch and the reason: a private page named (the rule every audit row is judged by) or a `<private>` region; when it holds, the shared row keeps only the attestation and says the mutations were withheld, so an apply whose reason the store would move to `private` is still attested in `shared`.
4. **Private evidence (3.18).** A private `apply-evidence` event never changes a shared preference's status, confidence, evidence timestamps or evidence sections, which dream writes to `shared` for every machine and remote caller; it counts toward a preference that is itself private. Every number derived from evidence that lands in `shared` follows the same rule: a merge copies each private evidence record of the drop as a private record (each copy keeps its source's partition), and its sums count a private use whenever the keep it lands on is private, and the shared and the private copies are written as two store writes, one per partition, since one write lands in one; the merge's log event and audit trail carry the sums of the shared evidence for a shared preference; dream compares a preference's counters against the ones the scan would count, so a shared preference with private uses settles instead of being rewritten every pass. A `preference-evidence` record in `private` no longer makes its preference private (before, the first private use moved the whole preference into `private` on this machine, where every later write followed it). The counters fold the partitions a machine holds, so a local caller on a machine that holds `private` sees its own private uses counted: that is the local view the event may affect, and it is never written back. A caller below local reach is shown the counters a machine that holds only `shared` folds: each preference of the store fold carries both, and the MCP server runs every tool call and resource read of a remote transport in an ambient scope (`store/caller-reach.ts`) that the preference facades and the rebuilt preference pages read, so the MCP tools, the `brain_context` digest, the operator snapshot and the review candidates all answer with the shared counters there. The device-local digest cache is always rendered with nothing withheld, since only local readers are served it; a remote caller gets its own render.
5. **Seen-shards ledger (3.21).** Every read-modify-write of the ledger runs under the device-local lock of the ledger file and re-reads it inside the lock, so a tracking read and a partition leave in two processes never undo each other. The lock guards the ledger alone and takes no other lock inside it, so a reader that holds a store lock may take it; a tracking update waits at most half a second and then skips, which only delays tracking to the next read, a skipped change stays queued in the process, counts as seen in its next listings (so a shard it names is still reported once gone) and is written with its next update, which a listing with nothing new also tries (a change for a partition the machine no longer holds is dropped then, and a partition leave drops its own process's queue for that partition), so a skip delays tracking, it does not drop it; and after a skip behind a lock one holder has kept the whole wait and longer (a crashed process's) the process leaves the ledger alone for ten seconds without waiting, so such a lock costs a hook one wait, not one per listing, while a lock other processes take and release in turn backs nothing off, whatever its directory's stat says (a released lock directory can linger with its old stat on Windows); the leave waits the full lock budget and refuses as before.

### D16. Topics as built (phase 3, tasks 3.1 to 3.3)

Details the specs leave open, settled for the first part of phase 3:

1. **Identity and envelope.** The topic id is a ULID minted by the writer of the `topic-create`, carried in the envelope `topic` of every topic record (all in the `topics` stream); the first create in fold order fixes the scope (`personal` or `project:<project>`, also the envelope `scope`) and the creation time, and a second create of the same id only offers its title, description and goal to their registers. A non-topic record belongs to the topic its `assign` names, else to the topic its envelope names (`topicOfRecord`).
2. **Items.** Decisions, open questions, log entries and milestones are list items keyed by an `item` id (the creating record's id when it names none). Each item, its owner topic, a milestone's completion and a question's resolution are registers; `removed: true` is an item's tombstone. A record that names an existing item with another kind is rejected. A log entry carries a `class`; only `routine` stays off the page, and `note` is a line the user wrote into the log section. A decision log event a topic holds is shown as a decision item derived at read time, not recorded (D17 item 8).
3. **Undo.** An `undo` voids the record it names when its authority is at least that record's, and can itself be undone; an undo cycle (only a forged one) is cut where the walk in canonical record order meets it again, so its outcome is deterministic on every machine. An undo of an `assign` and an `unassign`, by the user or an agent (not by a decision model), record a blocked route, which the dream planning of task 3.4 reads so it never routes that record to that topic again.
4. **Proposals.** A goal offer that comes after the winning goal and loses to it is a proposal, rendered as an open question attributed to its agent (spec "User rewrites the goal"). A `milestone-done` counts from the user, or from an agent with `evidence`; one from a decision model or from an agent without evidence is a "looks done, confirm" proposal. A model `question-resolved` is a "looks answered" proposal.
5. **Merges and splits.** A merge resolves the merged topic to its target (`canonical`), applied in fold order of the winning merge records, skipping one that would close a cycle or names a topic that does not exist; the target's page carries both topics' items and names the merged one in its related section, and the merged topic's page is removed. A split moves the listed items (their owner register) and record assignments. Both are written only on the user's confirmation (D9), so they carry `human` authority in practice; the fold applies them by the usual precedence.
6. **Partitions.** A write is one store operation in one partition (`topics/write.ts`): `private` when asked, when a `topic-create` in it has the personal scope and the caller did not ask for `shared` (spec brain-store "personal-scope topics SHALL default to private"), or when any topic it names lives in `private`, so a private topic's events never land in `shared`. The writer judges this from every partition the machine holds whatever the caller's reach, and refuses when a topics shard cannot be read in full. A topic is private when its first `topic-create` sits in `private`; an item is private when any of its records does. A caller below local reach folds `shared` alone (`topics/read.ts`).
7. **Private topics stay off the view.** The view renders from `shared` records only (phase 2), so a private topic, an item created in `private`, any record written to `private` and a shared record that carries a `<private>` region never reach a page. An item created in `shared` keeps its shared text on the page after a later edit of it lands in `private`: that edit is not shown, so nothing private is published, but the item does not leave the view; taking it out would be a separate decision. This keeps the phase 2 promise that a phone that syncs only the view sees nothing private, and it means a personal topic is not in the view by default. The spec scenario "User asks for a topic" for a personal matter therefore holds for a personal topic the user asks to keep in `shared`; whether the view should show private topics on a writer that holds `private` (with an opt-in shared setting and private ingestion of their edits) is left to the owner.
8. **Page layout.** `topics/<YYYY-MM-DD>-<slug>/topic.md`: the topic's creation day (UTC) and a slug of its current title (letters and digits of any script, joined by hyphens, at most 48 code points, `topic` when empty); a second topic that takes the same folder gets the last six characters of its id appended. The id comment line also names the topic (`topic=<id>`). Required sections are the title, the description (a generated placeholder when none), the status line and the related section (which names at least the scope); the goal, milestones, decisions, open questions and log are left out when empty. Decisions and the log are newest first; open milestones come first in the order recorded, then done ones newest first; goal proposals follow the open questions.
9. **Page budget.** Per section: at most 10 done milestones, 25 decisions and 15 log entries stay on `topic.md`; the oldest over that, and every resolved question, move to `archive.md` in the same folder, linked from the related section. Open milestones and open questions never move, so a topic with more of those than fits is the one case where the page is longer than its budget.
10. **Retiring pages.** A page in `topics/`, `reports/` or `sources/` that has a render record but is no longer rendered (a rename, a merge, an undone create, a removed report) is removed by the view writer at the start of its pass: an edit it carries and its conflict copies are ingested first, the page leaves its name by one atomic rename (so a racing edit is captured), and the user's companion files of a renamed topic's folder move to the new folder. An edit that renames the topic (its title line) moves the page on the next pass.
11. **Edits of topic pages.** A changed line of a topic page or its archive maps to the topic record that says the same thing, with `human` authority (`view/topic-edits.ts`): the title, description, status, goal, an item's text (decorations stripped in every view language), a ticked milestone, a deleted item (its tombstone), a deleted goal proposal (an undo of the agent's goal record) and a line added in an item section (a new item). A line this mapping does not own takes the generic phase 2 correction of the view. A done milestone's line key names the record that completed it, so unticking it on the page writes a human `undo` of that record and the milestone is open again.
12. **Reports and sources.** `reports/<entry>.md` and `sources/<entry>.md` render from the `lane-entry` records of the lanes `reports` and `sources` in `shared`, leaving out removed entries, entries whose fields reserve them as private, records with a `<private>` region and entry ids that are not plain file names. A body line's key is a hash of its text and occurrence, so a correction follows the line while the report keeps it.
13. **Note-tool refusal.** The note tools' view-folder guard (phase 2) names the topic event tool (`brain_topic`, `o2b topic`) for a path in the view's `topics` folder, and the report and source tools for `reports` and `sources`; at the vault root the guard also owns those three folder names.
14. **Digests.** The state digests (D6) hash a fourth fold, `topics` (`topicsFingerprint`: every topic, the assignments, blocked routes, voided records and rejected ids). The hash is optional in a digest, so a digest an earlier release of format version 1 published still parses, and two digests are compared on a fold only when both carry it; the format version does not change.

### D17. Topic planning, the topic tool and the CLI as built (phase 3, tasks 3.4 to 3.6)

1. **What planning reads.** The candidates are `signal` records and the log events a person reads (`note`, `decision-record`, `decision-resolved`), with their text, project and session (`topics/candidates.ts`). The project is the record's `project` field (a signal's frontmatter, a log event's body), normalised as every scope key is. The session is the record's `session`, else its `session_ref`, else the device, agent and UTC day that wrote it, so one agent's records of one day on one machine count as one session. A signal a `signal-removed` record forgot is not a candidate.
2. **Deterministic fallbacks only.** Until the decision-model uses of phase 4, routing and grouping use subject words (letters, combining marks and digits of any script; a decision event reads as its title with the option chosen, an older event without a title by its decision page's; four or more code points, a short list of common English words dropped). A record routes to the active topic of its scope whose head (title, description, goal and item texts) shares the most words with it, at least two and a fifth of the record's; a route the user took back is never taken. A record with no project routes only to a personal topic and never makes a topic: personal topics are made on request. A group is grown greedily in record order (a record joins the first group it shares two words with); one of at least `topics.new_min_records` records from at least `topics.new_min_sessions` sessions becomes a topic titled by its three most frequent words (a tie goes to the word its first record says first; a word its records write inside one hyphenated compound more often than alone is titled by that compound, named once, unless a part of that compound is already in the title; on a tie the word alone is used) with its first record's text as the drafted goal. A record any `assign`, `unassign` or `split` ever named (`touched`, voided ones included) is routed but never grouped again, so a topic the user undid is not recreated from the same records.
3. **Who and how.** Planning runs on the view writer only (the same view-writer records as the render), under a device-local lock, and reads every held partition inside the lock and refuses on a partial read; the second of two passes therefore sees the first one's topics and assignments and creates nothing twice. Its records are `agent` records of the dreaming agent. A create and its assigns land in `private` when any member is private; a route lands in `private` when the record or the topic is; a private record on a machine without the partition is skipped and counted. The dream pass runs it before the render (`brain/dream-tail.ts`), so the new topic's page is written in the same pass.
4. **Proposals and prompts.** Two active topics of one scope whose heads (title, description, goal) share half their words (Jaccard) are proposed for a merge; a topic whose own records group into two groups that would each make a topic is proposed for a split; an active topic with no record for `topics.quiet_days` (a new shared setting, default 30) is offered for a status decision. Nothing is written for them: the dream report lists all three, and the markdown digest gains a `## Topics` section with the merges and quiet topics and the command for each, rendered at the caller's reach and absent when there is nothing to ask, so a digest without topics is byte-identical.
5. **Undo.** `o2b topic undo <record>` (and `brain_topic` `undo`) writes a human `undo` naming a topic record the caller can see; the dream report prints that command for every create and route.
6. **The topic tool.** `brain_topic` and `o2b topic` share one implementation (`topics/actions.ts`). `o2b topic` writes human records and its `record` verb agent ones; `brain_topic` writes agent records by default, and the caller can name `human` with `authority` except below local reach (D18 item 5). Below local reach the fold holds `shared` only, and every write first resolves the topics it names in that fold, so a private topic answers "no topic with id" exactly as an unknown id does. `show` renders the topic's page with private items for a local caller (`topicPages` with `includePrivate`), never for the view. `osb://topic/{id}` answers the same page and the absent-topic error below local reach.
7. **Rule topics.** The preference-slug internals of the query and resource layers are named `ruleTopic` (`queryByRuleTopic`, `readRuleTopic` and their renderers); the resource is `osb://rule-topic/{slug}`, and `osb://topic/<value>` serves a topic when the value is a ULID and the rule topic otherwise, as the alias for one minor version. The `brain_query` tool's `topic` argument and the persisted `topic` field of signals keep their names (design D8).
8. **Held decisions are decision items.** D10 gives `event_kind` the deterministic answer "the kind the agent passed": `brain_decision` (and `o2b brain decision record|resolve`) write `decision-record` and `decision-resolved` log events, whose kind the agent named. A topic that holds such an event shows it as a decision item with no model (`topics/held-decisions.ts`). The item is derived when a page is rendered or `show` reads it, from the records the reader holds, and is never written: the view render derives it from the `shared` records without a `<private>` region it already reads (its read keeps `decision-outcome` events too), `show` (and `osb://topic/{id}`) reads the `log` stream of the partitions the caller may read when the topic holds records. So it exists exactly while the topic holds the event (an undo of the `assign` or of the topic takes it away, a topic made earlier gains it at its next render, a second pass and a second view writer write nothing), and it follows its records' partition and reach. The events that name one decision page (a resolve writes the minted page's `decision-record` and the `decision-resolved`) give one item, keyed by the smallest of their ids, marked as a resolved open decision when a `decision-resolved` is among them, with the newest `decision-outcome` of the page as its outcome; its text is the chosen option with `<private>` regions removed, as planning reads it. Nothing is derived when any topic record ever named one of those ids as an item of the topic, a merged one or one it was split from (`TopicFold.itemRecorded`, removed items included): a decision model's `event_kind` item (its id is the record id) or the user's edit or deletion of the derived line (keyed by the item id) wins, so there is never a second item for one decision; the user's item of an edited line keeps the decision's time, so the line does not move on the page and meet the user's copy at its old place. On the page a derived decision takes only the slots the recorded decisions leave within the budget (D16 item 9); the rest go to the archive, so no recorded item, the user's included, moves for one. Rejected: the planner writing the `decision` topic record a `brain_topic` call would write (a new automatic writer: its partition, idempotence across passes and machines, the dream report, an undo of the assignment that must also take the item back, and every later outcome or resolution would need another write, plus the migration-gate and write-site censuses), and a derived item in the fold itself (the fold reads the `topics` stream only, and the digests would change with the log).

### D18. Topics: review fixes (phase 3)

1. **Paths from records.** The view writer acts on a page path from a record only when it has exactly a shape the renderer writes (`topics/<YYYY-MM-DD>-<slug>/(topic|archive).md`, `reports/<entry>.md`, `sources/<entry>.md`: forward slashes, no `..`, no `\`, no empty segment) and resolves strictly inside the view folder (`view/page-path.ts`). No folder below the view folder, nor the page itself, may be a symbolic link, and the real path of the page's folder must lie inside the real view folder; this check also guards live page writes and both folders of a companion move. Any other path in a `view-render` record is ignored: a device that syncs `shared` can write any record. A Windows device name (`con`, `nul`, ...) is never a retiring page, and a retiring page that is a live page's file under another case (a case-insensitive file system) is not retired.
2. **Folder slots.** Retiring happens in `view/retire.ts`. A live topic page whose last render record names another topic (the id line on disk decides only for a page rendered before render records named their topic, since a user's edit or a sync merge can change it) is retired first (its edit ingested, its folder's companion files moved to that topic's current folder), then the pages no longer rendered. `view-render` records name the topic of a topic page, so the companions of a page already gone still follow their topic.
3. **Planning and the writer protocol.** Planning uses the render's gate: the writer releases on a pending request, a writer by its own fresh claim waits until the render settled the claim (`claimSeen`, read only, so the render's own wait is not spent), and the gate is asked again under the planning lock. The lock waits at least 30 seconds, and a pass whose topic records changed between its read and its writes (a lock taken over from a holder that looked stale) writes nothing (`raced`).
4. **Items per topic.** An item id is its topic's own: the fold keys an item by the topic that first recorded it and the id, and a topic an item was split into finds it by its current owner. A `record` that names an item (an edit, a completion, a resolution) must name an item of that topic of the right kind; below local reach a `record` may not pick a new item id. Unknown `record` fields are refused.
5. **Authority.** `brain_topic` writes `agent` records unless the caller names `human`, which is refused below local reach; `o2b topic` writes `human` records (the user runs it), and its `record` verb `agent` ones unless `--as-human`. The agent's goal therefore stays a proposal under the user's. A request that reaches `brain_topic` over a remote transport is recorded as an `agent` record: the transport cannot prove the user is behind it. Taking a route back blocks it whoever writes the undo or unassign, the user or an agent; only a decision model's leaves the route open, so an undo through `brain_topic` stops re-routing as `o2b topic undo` does.
6. **Privacy and delivery.** A shared record that carries a `<private>` region makes its cluster's topic private and is withheld from remote reads of topics; the topic page `show` and `osb://topic/{id}` return is fenced below local reach; an unreadable-shard refusal names no shard below local reach; topic titles and descriptions are one line; review answers and the digest's topic section are empty over a partial read.
7. **Resources and the view at the vault root.** `osb://topic/<value>` falls back to the rule-topic reader when no topic the caller sees has that id. With the view at the vault root, the note tools refuse only the view's own pages (and their conflict copies and temp files) in `topics/`, `reports/` and `sources/`, and the folders that hold them as containers; a user's own note in those folders stays writable. Report and source ids that differ only in case render one page, and Windows device names none.

8. **PR review follow-ups.** A topic starts `active` without the create claiming the status register, so the first `topic-status` of any authority applies (a later human one still wins). The planner cuts a drafted title to the record limit and checks every create as the fold does before it writes anything of the group. Below local reach every topic text of `list` and `show` is fenced, not only the page. After a merge an item id two owners share is refused as ambiguous until `record` names the `owner`. An undo of an undo is checked by the record it names, so an undone create can be taken back. A line the user adds to a topic page gets an item id derived from its topic, section and text, so the same line in a page and its conflict copy is one item. A private item's words never route a shared record. The view writer never reads a page name that became a symbolic link (it checks each name it reads or captures), moves a companion file only onto no name (a link, then an unlink), honours the pass's time budget while retiring, and takes a retiring page's owner from its last render record before its id line. The dream pass forwards its config path to topic planning and the view render, counts topic writes as a change, and skips planning once its deadline has passed. The folder of a topic never repeats another topic's, whatever a title ends in.

9. **Re-review follow-ups.** An undo is private when the record it names sits in `private` (an undone private create takes its topic out of the fold, so the topic alone cannot tell), so neither a private topic id nor a private record id reaches `shared`. The fold reports, per head field (title, description, goal), whether its winning record is private, and only shared head text and shared items route a shared record. A `record` with an `owner` names an existing item of that owner, and the owner must be the topic or one merged into it; otherwise it is refused as an absent item is. The planner cuts a drafted title in UTF-16 code units, the unit of the record check, after capitalizing and never inside a surrogate pair. Below local reach the scope of `list` and `show` is fenced like the other topic text. A name that is not a regular file (a folder) at a live topic page reports that page as refused and the rest of the pass renders: the disk is read for an owner only when no render record names one. A page is read through `O_NOFOLLOW` and a check of the opened descriptor where the platform has them. A companion move leaves a file in exactly one folder: when the old name holds another version by the time it would be unlinked (a sync tool delivered a newer one), or cannot be unlinked (Windows reports a file another program holds as `EPERM`, the code it also gives for "no hard links"), the new name is taken back.

10. **Second re-review follow-ups.** Planning checks the view writer again from the catch-up read it plans from, so a move that arrives after the gate under the lock read the settings still stops the pass (`not-writer`). The dream pass asks its deadline again under the planning lock, after the read and before the first write, and a pass past it writes nothing (`deferred`). A write that fails after others landed reports `error` with the topics created and records routed before it, each with its undo command, and the dream summary counts them as a change. A `split` request takes only items the topic shows and writes the split of an item of a merged topic under that topic, the item's owner (the fold looks up a split's items by the topic it names); an id two merged owners share needs `owner`. An item id is refused for a new item of a topic only when a split moved that topic's item of the id to another topic: the fold still resolves the id to the moved item. A removed item stays its topic's, so its id can be recorded again. A `decision` record that leaves `serves` out keeps the links the item has, so a decision reworded on its page keeps the milestones it serves, and `"serves": []` clears them. When topics exchange folders, each retiring page moves only the companion names its folder held before any move of the pass. A companion move never unlinks a live name: the source and, when a move is taken back, the new name are each renamed to a temp name first and removed only when they are the version this move checked or placed, so a version a sync tool delivers under either name meanwhile is put back. A conflict-copy name that is not a regular file (a folder, a symbolic link) is refused where it is, and a capture that meets one puts it back under its name without replacing a name that exists. A conflict copy is taken out of its name before it is read, in a render and while retiring, so a copy written again after that read stays for the next pass. A private record routes by the private head text of a topic too, since its assign lands in `private`, and so does any record routed to a private topic; a shared route still uses shared text only. An edit, completion or resolution of an item that has a record in `private` is written to `private`, whatever the caller asks. `o2b topic split` takes `--owner` as `brain_topic` does; a split whose named topic moves no item of its own carries only its records. `brain_topic` refuses a `private` or `removed` that is not a boolean instead of dropping it. A dream pass plans on its own clock when it has one, and its undo commands name the config it ran with. A topic's activity time includes the records of topics merged into it and a split that hands it items or records. An item's privacy counts its completions and resolutions, whose evidence and answer are its text, so a later one written without the flag stays private. A route taken back from a topic is also blocked for the topic it merged into. Companion moves resolve each path once and use path-based calls: the runtime has no descriptor-relative rename or link, so a folder swapped for a symbolic link between the check and the call is not caught. That needs a process with write access to the view folder at that instant, which can already change the user's files directly.

### D19. Schema field lists, personas and the shared namespace (task 3.12)

Three questions the store left open after phase 2, settled by the option that fits the store already built (append-only records, order-independent folds, human over agent over model, shared and private partitions) with the least new machinery.

1. **Schema field lists merge per entry.** A schema field (`brain.schema.<field>`) was one settings register over the whole list, so two devices that each added an entry before they synced kept only the later list (a whole-list last writer wins). A schema apply now writes one `setting-entry` record (`{ authority, key, entry, present }`) per entry it adds or removes, never the list. A settings key that holds such a record folds per entry (`store/fold-setting-lists.ts`): each entry is one register under D4, keyed by its slot, the entry in the normalised form the pack parser reads (NFC, quotes stripped, trimmed, lower case, each side of a `name=value` line on its own and each side of a `->` pair too), or for the keyed lists (`prefixes`, `expert_routing`, `attributes`, `frontmatter_tiers`, whose `name=value` lines hold one value per name) the normalised name, a compound `type.field` name of `attributes` and `frontmatter_tiers` split at its first `.` with each half normalised on its own (the split function is the parser's own, `splitCompoundSchemaKey`, so `paper . year` is never a second slot beside `paper.year` and never repaired away as a dangling entry), so a changed value replaces the old entry and a variant spelling of one token is the same slot, never a second one. Only the keys `brain.schema.<field>` take entry records; the fold rejects an entry record for any other key, so a key that holds one value (a human `permissions.document`, a boolean, an object) stays on the plain register and no entry record can turn it into a removed list. The other way round too: a `setting-set` of a `brain.schema.<field>` key whose value is no list of one-line scalars (a string, a number, an object, an element with a line break) is rejected by the fold, so it can neither win the plain register and hide the stored list from the pack reader and the attestation, nor remove every entry of a key folded per entry, nor read as several pack lines; the settings writer already refuses such a value. An add on one device and a remove of the same entry on another resolve as every register does: the stronger authority, then the later clock. A whole-list `setting-set` (the migration's import, `o2b brain settings set`) offers every entry the key ever named, its own as present and the rest as removed, and a `setting-unset` offers all as removed, so whole-list histories resolve exactly as the register did; a key with no entry record folds as the plain register. The list is ordered by the fold order of each entry's deciding record. Rejected: keeping the whole-list register and asking the user to re-apply after a conflict (silent loss is the defect the task names); a three-way list merge against a base the record would have to carry (more machinery, and it needs the base both devices saw, which delayed sync does not guarantee); add-wins or remove-wins as a special rule for lists (a second precedence rule beside D4 for no gain).
   1.1 **Authority per entry.** The writers refuse an agent change the fold would ignore. An apply's entry change is refused when its slot is decided by a stronger authority; a slot no record named yet is decided by the whole-list records alone (the strongest `setting-set` or `setting-unset` of the key), never by the newest entry record of another slot. For a key folded per entry, an agent's whole-list `o2b brain settings set` or `unset` (MCP `brain_settings`) is refused when any slot it would add, remove or respell is decided by a stronger authority, and an accepted write reports the folded value, not the requested one. A key not yet folded per entry keeps the key-level refusal.
   1.2 **References across fields are repaired on read.** The fold merges per field, so a `remove_type` on one device and an `add_alias` or `add_prefix` for that type on another meet in a pack no apply could produce. The fold cannot refuse a record that arrives later, so the rule is enforced on the read side: the pack built from the store drops every reference to an undeclared token (aliases, prefixes, extractable entries, expert routes and attributes of a token the vocabulary does not hold, a link constraint pair whose source or target the vocabulary does not hold, and the constraints of an undeclared link type or of one left with no pair), the cascade `remove_type` and `remove_link_type` apply (`remove_link_type` drops the pairs of other link types that name it as an endpoint unless a vocabulary type of the same token keeps it declared). A pair is dropped rather than kept as inert: the indexer reads a page's type from its frontmatter `type:`, which removing the type from the vocabulary does not rewrite, so a kept pair would still allow or refuse typed edges of such pages, and an apply refuses a pair with an undeclared endpoint, so a machine that reads `_brain.yaml` never holds one either. The drop is deterministic, so every machine reads one consistent pack and a later apply never fails on a dangling reference. The next apply writes the drop as entry removals, so the records converge too; a removal the applying authority may not write (an agent, an operator's entry) is skipped, since every reader drops it anyway.
   1.3 **What an audit row attests.** A pack merged from two applies is no single apply's output, so its digest matches no audit row. Each apply's row also names records (`decided`): the records this apply wrote, plus the deciding records that rows this machine has seen already attest. A row names each record as `<id>:<sha256>` of the record's canonical JSON, never by id alone: a record's checksum covers its body, not its id, so another version under an attested id would otherwise pass as attested. An apply reads the store's schema records once, under its lock (`readStoreSchemaPack` in `brain/schema-pack.ts`): the pack in force, the records deciding it and the stored field lists a repair compares against all come from that one fold of the shared settings stream, so the race is impossible rather than unlikely. A record that syncs in while the apply runs is neither part of the pack it builds on without being among the records it checks, nor attested by its row, nor removed as a repair: a repair removes only an entry the pack in force dropped on read from the same field lists (item 1.2), never one the read did not hold. A repair removal also names the record that decided the entry's slot in that read, and the settings writer skips it when another record decides the slot by the time it is written (a replacement another device wrote meanwhile). Sync delivers a peer's record at any time and no lock orders it against this machine's append, so a write-time check alone still loses a replacement written before the repair and delivered after it, whose clock is lower. The repair is therefore written as a conditional removal (`if_decided_by`, the record it judged): the fold applies it only while that record decides the slot among the key's unconditional records, and ignores it otherwise, whatever its clock and the delivery order. So a repair never removes what it did not judge; skipping or ignoring it is always safe, since every reader drops the dangling entry anyway. Rejected: re-checking the slot under the shard lock right before the append (it narrows the window and closes it only against writers on this machine, not against sync). `if_decided_by` belongs to `setting-entry` alone: on a `setting-set` or `setting-unset` it is no field of the kind and is ignored, as the format ignores every field a kind does not define, while on an addition, or empty, it is a malformed `setting-entry` and the record is rejected. A key whose records name no entry at all once the inapplicable conditional removals are dropped (an empty whole list, an unset) is a removed key, won by its strongest, then latest, record as the whole-list register would win it; the list fold never throws on any record set, which a seeded property test over small random record sets pins together with order independence. The integrity read takes the pack's digest and the records it checks from one read the same way. Never every record that happens to decide the pack: one apply would then attest, on every machine, a record no apply wrote. A store-only pack that differs from the newest digest is still `ok` (`merged`) when every record deciding it is named by some row. A deciding record no row attests under an apply is a finding: the apply refuses with `unattested_schema_records`, naming the records, and the integrity read reports the pack as `modified`, naming the same records (field `decided`), even when the pack digests as the newest row recorded (a record that sets an entry the pack already held changes no digest but still decides the entry), and even when the records leave no pack at all (an unattested removal of the last entry of the only schema field): the check for unattested records runs before the pack-absent answer, which stays `unverified` (`config-absent`) only when every deciding record is attested. Only a store whose rows all predate `decided` keeps the digest comparison alone. The operator may adopt them with `o2b brain schema apply --adopt-unattested` (human authority only; MCP has no such option), with or without mutations (on its own it is an empty batch, and only on a store-only machine), and the row records them as `adopted` with the operator as `adopted_by`. Adoption alone writes no entry record, not even the repair of a dangling entry: it attests, it does not edit. The migration's import writes a baseline row (`schema_import_baseline`, no digest) attesting the schema records it wrote. A store whose rows all predate `decided` keeps the digest comparison: there an apply counts the records deciding the pack as attested only when the pack in force is exactly the newest apply's output. The attestation reads the same pack fields the pack reader does, the field names the pack parser reads and nothing else, so a record under `brain.schema.` that is no pack field (a name the parser does not read, a dotted key, a value that is no list) changes nothing attested.
   1.4 **Versioning.** No released version of Open Second Brain contains the brain store; the store ships for the first time in the release that also carries `setting-entry`. So no earlier release can meet the kind, and format version 1 includes it from the start. From that first release on, the versioning rule of the format (`store/FORMAT.md`, Versioning) applies unchanged: a later change that a reader of the released format would misread raises the format version, so that reader skips and reports the newer records instead of folding a different value.
2. **Personas are records.** D14 item 2 already folds personas as `lane-entry` records of the lane `personas`, and the panel read them from the fold, but nothing could write one on a store-only machine, where there is no `Brain/personas/` folder to edit. The lane page layer now writes and removes them through `o2b brain panel persona-set <slug> [--lens L] [--file F]` and `persona-remove <slug>` (`personas` lists them), with human authority from the CLI: a note on an unswitched machine, a record on a store-only one, with or without a vault. A persona curated on one machine is the lens on every machine of the store, and two devices editing one persona resolve by D4. The verbs run the lane write guard first, as every lane write: a frozen machine refuses them in both modes, and a running migration refuses them on a machine that has not switched; on a store-only machine the guard checks the store identity in place of the vault marker (D14 item 13) and keeps the freeze, as the store-mode settings writer and the store-only schema apply do, while a migration gate left naming the vault refuses nothing there. The verbs then refuse a page of another kind at the persona's path, refuse to replace a persona that lives in `private` (the lane writer keeps a replaced entry in its partition and never lowers its privacy, so the operator removes it and sets it again), and refuse a private persona by name: a lens or prompt with a `<private>` region or naming a private page would be stored in `private`, which machines that do not hold it never read. A prompt holds at most 16 KB (every panel step carries it, and the record syncs to every machine), a lens at most 200 characters on one line, Unicode line separators included. On an unswitched machine with the phase 1 dual write on, `persona-set` also writes the entry to the store, so `persona-remove` there dual-writes the stored entry's tombstone, and a persona removed before the switch is not back after it; this is the lane page layer's removal and move (`store/lane-dual-moves.ts`), so every lane's removed or moved page (a pledge, a staged folder, an archived dead end) leaves its stored entry the same way. A page that never reached the store is removed as a file alone. The records of one removal or move, a folder's included, are one store operation built from one fold of the lane entries, so an entry's value and its partition come from the same read. A move is the write of the destination page plus the removal of the source, judged as those two writes would be judged, in both modes and for a page and a folder alike; one table-driven test checks it over every state a move can start from (`tests/core/lanes/lane-move-table.test.ts`). A moved entry is built from the page as it is on disk after the rename (a legacy-only edit the store never saw included; when nothing the store would import is there, the move removes the source entry and the destination entry the rename overwrote, and writes nothing else), lives where the old entry lived, or in `private` when the page is private by its own content, the fold may miss a record, or the destination it replaces is private (its stored entry lives in `private` or its fields reserve it, or, on an unswitched machine, the legacy page the rename replaced was private by its frontmatter): the rule of a write over that page, since nothing lowers an entry's partition, and a move is a write at its destination. A move that replaces a shared destination entry with a private one writes that entry's shared tombstone first (D14 item 18), the store-only move too. A page the store never saw, renamed over a path whose entry the store holds (a single page, or a file of a folder moved onto stored entries), is dual-written as the write of that page alone (there is no source entry to remove): the page as it now is on disk, judged as a fresh write would be (the replaced entry or legacy page private keeps it private, its own content, a fold that may miss a record), the replaced shared entry's tombstone first when the new value leaves `shared`; when no page the store would import is there, the stored entry's tombstone alone. A folder's stored entries are paired from the entry ids below the source and the destination folders, never from the disk, so a link where an entry's file was does not hide that entry. Each moved entry is placed by itself (D14 item 18), so a private page of a folder does not raise the others, and the lane's private-when-held rule does not apply to a move (no caller moves a page into such a lane). So the destination's stored entry never stays live with content the tree no longer has. A move whose source is a lane entry and whose destination is none (outside `Brain/`, or not in a lane folder) is refused before anything moves, in both modes: an unswitched machine used to rename it and write the tombstones, while a store-only machine has no file to leave there and its tombstones alone would lose the page. A store-only move of a single page onto itself (the same path, or one that normalises to it, a trailing slash included) writes nothing, like every same-identity move. A dual-written move builds the new entry from the legacy file even when the store holds a newer value from a switched peer: the legacy write wins during the trial (D11), so a peer's newer value of a page this machine moves is replaced by the file's; no staleness guard is added, since the trial's rule is that the legacy tree is the truth until the switch. The page at the new path is never read through a symbolic link, at its own name or at a folder below `Brain/`, nor when it is a special file (`openRegularFileForRead`, the rule of the migration's legacy scan, which never imports such a page): it writes the tombstones of the old entry and of the destination entry the rename overwrote, so a link moved as a lane page cannot carry a file from outside the vault into `shared`. A folder is never moved into its own subfolder nor into a folder that holds it, refused in both modes before anything moves: the rename refuses both (a folder cannot move into itself, and the folder that holds the source is never empty), and on a store-only machine one entry's destination can be another entry's source in the same batch (`s1` moved to its parent, holding `s1/z.md` and `s1/s1/z.md`), whose tombstone, written after it, would remove the entry the batch just wrote there. Refusal was chosen over writing every tombstone of the batch before every new entry: that order keeps every entry, but it accepts moves the rename refuses, so the two modes would end in different states, and a move into an ancestor would merge the folder's entries into the ancestor's own. With overlapping folders refused, the only destination that is also a source is the folder moved onto itself, which writes nothing. A fold that may miss a record is one with an `events` shard it could not see or read only in part, or a record in `private` whose body blob has not arrived, quarantined on this machine or not (a quarantine lets the shard read as whole, yet the record is still left out, and it may be the newer private value of the entry that moves): one predicate (`laneFoldIncomplete`) answers it for every lane write, move and privacy read, so a quarantined blob in `private` no longer lets a lane page into `shared` while the record waits. A record in `shared` whose blob has not arrived does not count: every writer judges a value's fields before it places the record, so a record in `shared` never carries a value that makes an entry private, and leaving one record out changes an entry's winner only when it is that winner (the register keeps the last record of the strongest authority), so the fold without it is at least as private as the fold with it. Counting it would block every lane write on a machine that holds only `shared` until the lost blob arrives, which is what a quarantine is there to end. The table test crosses both with the move states. A move onto the entry it moves (the same path, or one that normalises to it) writes nothing; a case-only rename names two entries in the store, whose entry ids keep their case, so it moves the entry like any rename. Rejected: personas as files in the view folder, ingested by the view writer (a second edit path, and the view is rendered from `shared` only and written by one device, so a machine that is not the writer could not curate); personas as device-local files (machines would disagree on the panel's lenses).
3. **The shared namespace gets no store of its own.** The `shared_namespace` mirror wrote remember-writes into a second vault. A write to a vault that is store-only on this machine lands in this machine's brain store, which every store-only agent of every machine of the store reads: a store-only namespace is that store. So the mirror writes there when the origin record is not in it already (the origin vault still writes the legacy layout and dual writes are off), attributed by `origin_vault` as before, and refuses before any I/O when it is (a switched machine, a store-only origin vault, dual writes on), naming the reason, and when the machine has no store at all. Every check reads the machine config the caller names, the one its origin write used. A namespace path that is no directory (unmounted, missing, a file) is reported `failed` before any write, never taken for a store-only namespace. A second store would need its own store identity, clock floor, held partitions, seen-shards ledger, digest roster and index per machine for a fact every agent of the brain already shares; a namespace shared with a different brain stays a legacy-vault feature. Rejected: a `shared_namespace_store` root opened beside the machine's own store (all of that machinery, and one brain across vaults, D14 item 14, already covers one user's agents); keeping the blanket refusal (it also refused the case where the mirror is the only way the record reaches the store).

### D20. Decision-model uses and agent context as built (phase 4, tasks 4.1 to 4.5)

1. **Registry.** The nine uses are appended to `DECISION_MODEL_USES` in contract order after `recall_inject`; each is `off` unless `decision_model_uses` names it. The value is the floor skill attachment already keeps before its second request (`SKILLS_STAGE2_MIN_REMAINING_MS`), a twelfth of the default 3 s request timeout: a hosted round trip rarely answers in less, and a request that cannot finish may still be billed.

## Risks / Trade-offs

- [A fold bug makes machines diverge silently] → state digests with doctor alerts (D6), property tests that shuffle delivery order and duplicate lines, and a rebuild command.
- [Clock skew orders two concurrent edits against the user's intent] → authority precedence decides most conflicts before the clock does, and the losing edit stays in history.
- [The view writer is offline for a long time] → pages go stale but no data is lost; doctor on every machine reports it after 3 days and names `o2b view writer --here`.
- [A phone edit races a render] → re-check before the rename, and ingestion of the resulting sync-conflict copy as a human edit (D7).
- [Legacy writers on other machines keep writing during migration] → per-line journal, final delta pass, imports during the transition, and the legacy tree stays until every roster device has switched (D11, D11a).
- [Rollback after new writes] → replay into the legacy layout through exporters (D11).
- [Skills still tell agents to use `Brain/` paths] → skills rewritten in phase 2 and legacy-tree detection in doctor (D11, D12).
- [Large migration on a slow disk is interrupted] → per-item journal, `--resume`, and no source removal before verification.
- [Users sync the device-local directory by mistake] → it lives outside the store root by default, and doctor reports another device's id inside it.
- [A cloud-drive sync tool changes whole files under a writer] → one writer device per file; doctor reports conflict copies and torn middle lines.
- [The private partition is missing on a server agent's machine] → writes of private records refuse with a clear message; reads work on what is present.
- [Phase 1 dual writes double disk use for a release] → the flag is off by default and documented as a trial.

## Migration Plan

D11 is the plan, including rollback. The transition window ends per install when the legacy tree leaves the vault (D11a). Code for legacy reads and rollback stays for two minor releases after the release that ships the migration.

## Open Questions

- The weekly history page budget (lines per week) is to be tuned once the `human_readable` use has shadow data.
