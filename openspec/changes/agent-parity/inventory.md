### 2. The post-upgrade worker as the template

Claim-before-spawn, per `startSelfHealUpgrade` (`src/core/maintenance/ensure-current.ts:270-310`): check the failure marker's backoff first (`ensure-current.ts:279-281`), claim the lock with `{handed: true}` (`ensure-current.ts:285`), spawn only on a won token (`ensure-current.ts:291-303`), release the claim if the spawn throws (`ensure-current.ts:304-308`). The token travels as a CLI argument to the child: `["brain","upgrade","--vault",vault,"--self-heal",token]` (`ensure-current.ts:296`), and the migration worker hands the claim to its child's pid via `handAutoMigrationLock` after `startOnClaim` succeeds (`ensure-current.ts:480-500`; `startOnClaim` itself `ensure-current.ts:533-558`).

- **Spawn plumbing**: `src/core/maintenance/o2b-command.ts` — `o2bCommand()` builds the argv under the running runtime's absolute exec path, never a PATH lookup (`o2b-command.ts:73-99`); `spawnSelfDetached` spawns detached/`windowsHide`/`unref`ed with streams ignored (`o2b-command.ts:149-223`); the macOS SQLite env repair rides along (`o2b-command.ts:119-129`).
- **Failure marker + bounded backoff**: `src/core/maintenance/self-heal-upgrade-state.ts` — marker `self-heal-upgrade.json` under the per-device derived-store state dir (`self-heal-upgrade-state.ts:52,84-86`, via `machineStatePath`), shape `{failedAt, error, consecutiveFailures, pending, retryAfter}` (`:61-75`), cooldown `base 1h · 2^(n-1)` capped at 24 h (`:55-58,89-96`), backoff check `selfHealUpgradeBackoffActive` (`:147`), stale-lock takeover after 1 h (`:65`).
- **Lost-worker handling**: a worker that never confirms its claim is recorded as a failed attempt under that claim and starts the cooldown (`ensure-current.ts:464-479`, `recordLostAutoMigrationWorker`); a live-pid holder older than trust is `skippedRunning` unless the claim is undecided (`ensure-current.ts:453-462`); a parent that is still alive watches its child and settles the exit at once (`watchWorker`, `ensure-current.ts:510-522`).
- **Log**: each spawn opens a new attempt in a device-local stderr log, capped to 64 KB / keeps 16 KB tail (`autoMigrationWorkerLogPath`, `src/core/store-migration/auto-state.ts:213-215`; `WORKER_LOG_CAP_BYTES`/`WORKER_LOG_KEEP_BYTES`, `src/core/store-migration/worker-log.ts:17-20`; attempt header written before spawn, `ensure-current.ts:577-580`).
- **Record shapes / locations**: the lock and marker live under `machineStatePath(vault, DERIVED_STORE_DIR, …)` (`self-heal-upgrade-state.ts:21,84`); `machineStatePath` maps a vault-relative path to the vault, or the device-local `migration/local` folder once switched (`src/core/state/machine-state.ts:295-319`).

## 15. Risks and open questions (priority order)

1. **The closed-day fast path has no home today.** The check must read "one small machine-local record per brain" with no database opened (`brainstorm.md:77`), but the session start currently resolves the vault via `resolveVault` → machine config (`hooks/lib/hook-vault.ts:44-58`) and reads `Brain/_brain.yaml` for limits (`hooks/lib/active-context.ts:184-190`); on a store-only machine the record's key (brain identity) is not derivable without `resolveConfiguredStoreRoot`/`readDeviceId` (`src/core/brain/dream-owner/gate.ts:107-118`). Deciding where the record lives (per-store `deviceStateDirFor` vs `machineStatePath` under the vault) and what identity keys it is the first design decision; §3.
2. **`handleInitialize` is synchronous and cannot spawn.** Adding the check there is bounded (identity read only, `server.ts:648-675`), but a persistent MCP server handshakes once — the design already moved the check to "session entry" (`brainstorm.md:76`, Process section), yet most non-hook hosts (OpenClaw, Cursor, Gemini CLI, Copilot CLI, kiro, aider) have *no* session event at all (§1 table), so "one entry point per adapter" has no adapter surface to hook for them; the MCP instruction text or first tool result is the only carrier (§10).
3. **The 10-second hook budget is already spoken for.** `active-inject` shares 10 s with standing rules, scoped rules, head-select (half the ceiling, `process-ceiling.ts:94-95`) and fire-and-forget maintenance; a dream-claim + spawn on the due path must fit the same ceiling and the 9,000-char payload discipline (`host-context-ceiling.ts:64`) — spawning detached is proven (§2), but the due-path recheck-under-claim is new synchronous work on this budget.
4. **Claim-before-spawn for dream needs a lock with a stale policy that none of the three existing locks provides unchanged.** The self-heal upgrade lock is vault-scoped with a 1 h stale takeover (`self-heal-upgrade-state.ts:65`), the maintenance lease is a SQLite lease in vault-local state (`src/core/brain/maintenance/lease.ts:44`) — the brainstorm's own doubt about that lease living device-locally on a switched machine ("two machines can both hold it", `brainstorm.md:33`) applies verbatim to a per-day dream claim; cross-machine exclusion must come from the store (like the dream owner's pass lock, `constants.ts:27`), not the device state.
5. **"Last successful pass" does not exist; the three-day line would read a log stream, not a status record.** The only synced fact is the `dream` log event in the shared `log` partition (§6-7); a pass that ran but wrote nothing ("verified empty work", `brainstorm.md:79`) writes what? The `changed: false` no-op run writes no log entry (`docs/hermes-cron.md:78` — "no log entry written"), so silence is ambiguous between "ran, empty" and "never ran" — the trigger's cached line would misreport it.
6. **Adoption has no detection of the old trigger.** The design refuses a legacy-cron run with a removal hint (`brainstorm.md:107`), but no code identifies a pass as cron-born (§5, "not found") — a cron script runs the same `o2b brain dream` argv as a human, so the only discriminator is an env marker the old recipe does not set; the "legacy trigger from an older binary cannot honour the gate" risk (`proposal.md:53`) is already acknowledged and remains open.
7. **Recipe removal is byte-pinned and doc-ratcheted.** Removing the `hermes cron create` block, the `.hermes/.env` sourcing and `docs/hermes-cron.md` fails `tests/cli/cron-recipe.test.ts:157`, `maintenance-cron.test.ts`, `search-cron-template.test.ts`, `link-ratchet:check` and the install-doc conformance suite (§14) — the change must edit the pins and the ratchet in the same PR, and decide whether the printed recipes keep a neutral "your own scheduler" third section or drop to two paths.
8. **`discipline install` removal strands installed jobs.** The installer wrote entries into the user's `~/.hermes/cron/jobs.json` keyed by vault hash (`discipline-install.ts:85-101`); after removal no command can find or remove them, and the ownership entry that documents them (`ownership.ts:332-344`) would be deleted — the uninstall plan/uninstall-target flow (`src/cli/main.ts:1354-1372`) should name the leftover jobs file, or the 2.0 breaking change silently orphans daily Telegram posts.
9. **Digest-at-session-start collides with an already-full budget.** The digest lane must fit the 9,000-char ceiling beside standing rules, scoped rules, heads and pinned context, and the delivery-once guarantee needs the injection ledger (`active-inject.ts:447-475`) extended to a new content kind; for MCP-only hosts there is no push channel at all — only instruction text or a resource the agent must choose to read (§10), which is a weaker guarantee than the design's "delivered once at the next session start" (brainstorm.md:121).
10. **Discipline-in-doctor is fail-soft by construction; its alert must not become noise.** The store-side check list reports through `uncertain`, which deliberately does not feed the exit code (`src/cli/brain/verbs/doctor.ts:334-337`); a discipline alert demoted to `uncertain` would be invisible to `--strict` and CI, while promoting it to `warning` changes doctor's exit contract for every vault with a quiet day — the finding class (`DoctorFindings` stream) needs an explicit decision.
