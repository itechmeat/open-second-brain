## 2. Install targets and exactly what they write

Registry: `defaultRegistry` in `src/core/install/registry.ts:46`, populated by the barrel `src/core/install/adapters/all.ts:15-24`. Target vocabulary: `INSTALL_TARGET_ID`/`INSTALL_TARGET_IDS` `src/core/runtime/host-facts.ts:61-88` — `aider, codex, copilot-cli, cursor, gemini-cli, generic, grok, kiro, opencode, pi`. Every adapter's MCP payload comes from `buildPayload` `src/core/install/payload.ts:85-109` with `command` = **bare `o2b`** (`COMMAND`, `payload.ts:26`) resolved off PATH (Windows: `cmd /d /c o2b`, `payload.ts:49-55`), args `mcp --vault <vault>` (full) / `mcp --writer-only --vault <vault>` (writer), env `VAULT_AGENT_NAME`/`VAULT_TIMEZONE` (`payload.ts:129-134`), plus `--tool-profile`/`--host-target` for `HOST_PAYLOAD_TARGETS` (`payloadForHost` `src/core/install/payload-host.ts:105-131`).

Per target — what is written, and where the registered command is decided:

- **codex** — `codex mcp add/remove` subprocess when `codex` is on PATH (`applyViaCli` `src/core/install/adapters/codex.ts:275-295`), else TOML merge of `[mcp_servers.open-second-brain]` + `[mcp_servers.open-second-brain-writer]` into `$CODEX_HOME/config.toml` (`applyViaFile :297-311`, `codexHome :180`). Command shape: canonical payload verbatim (`tomlEntry :215-221`), identity-stamped by `payloadWithRuntimeIdentity` (`codexPayload :197-199`).
- **copilot-cli** — `copilot mcp add/remove` subprocess only (`src/core/install/adapters/copilot-cli.ts:173-202`); no file artifact.
- **cursor** — `~/.cursor/mcp.json` (`src/core/install/adapters/cursor.ts:19`) via shared JSON-merge `createJsonMcpAdapter` `src/core/install/adapters/_json-mcp.ts`.
- **gemini-cli** — `~/.gemini/settings.json` (`gemini-cli.ts:13`); **kiro** — `~/.kiro/settings.json` (`kiro.ts:17`). Same shared body.
- **opencode** — JSON/JSONC merge into `${XDG_CONFIG_HOME:-~/.config}/opencode/opencode.json(c)` under `mcp` (V1) or `mcp.servers` (V2) (`src/core/install/adapters/opencode.ts:78-100`), **plus a copied plugin file** at `~/.config/opencode/plugins/open-second-brain.ts` with a version-stamped header (`pluginPath :699-701`, `installedPluginContent` `src/core/install/opencode-plugin-asset.ts:29-38`, applied `:738-757`, verified `:788-810`).
- **grok** — MCP: `~/.grok/config.toml` `[mcp_servers.*]` where the command is rebuilt as **`process.execPath` (absolute bun) `run <REPO_ROOT>/src/cli/main.ts …`** (`grokMcpServers` `src/core/install/grok-asset.ts:51-62`; `REPO_ROOT = join(import.meta.dir,"..","..","..")` `:29`, `MAIN_TS :30`). Hooks: `~/.grok/hooks/open-second-brain.json` with **`bun run <REPO_ROOT>/hooks/<name>.ts`** per hook (`hookCommand :65-67`, spec `:94-185`, writer `grokHooksJson :208-222`; adapter writes it at `src/core/install/adapters/grok.ts:60-64`, `~/.grok` honoring an override `grok.ts:54-56`). **This is the one place already producing "absolute Bun + repo path" — but pointing into a clone/plugin checkout, not a registry prefix.**
- **pi** — symlink `~/.pi/skills/brain-memory` → `<plugin>/skills/brain-memory` (`src/core/install/adapters/pi.ts:57-77`, target `:64-71`); no MCP command line.
- **aider** — marker-fenced managed block in `~/.aider.conf.yml` (or `cwd/.aider.conf.yml`, `aider.ts:59-61`) + sidecar `<vault>/.open-second-brain/aider-context.md` (`aider-wrapper.ts:70-74`); no MCP.
- **generic** — prints the payload; writes only to `--out` (`src/core/install/adapters/generic.ts`; `ApplyOpts.outPath` `types.ts:101-104`).

The decision "plugin root vs clone vs `scripts/o2b-hook` vs bare `o2b-hook`" is made in exactly these places today:

1. `hooks/hooks.json:9,20,26,37,49,55,61,67…` — shell fallback chain `exec "$CLAUDE_PLUGIN_ROOT/scripts/o2b-hook" <name>; command -v o2b-hook && exec o2b-hook <name>` (Claude Code plugin).
2. `scripts/o2b-hook:31-70` (`resolve_root`) — priority `$CLAUDE_PLUGIN_ROOT` → wrapper's own realpath dir/.. → `$OSB_PLUGIN_ROOT`, first candidate holding `hooks/<name>.ts` wins.
3. `grok-asset.ts:29-35,65-67` — absolute `process.execPath run <REPO_ROOT>/…` (clone path).
4. `payload.ts:26,49-55` — bare `o2b`/`cmd /d /c o2b` off PATH (the `install-cli` symlink).
5. `src/cli/install-cli.ts:28-43` — the symlinks themselves point at `<repoRoot>/scripts/<name>`, `repoRoot()` derived from `import.meta.url` (`:30-33`).
6. Windows `.cmd` launchers embed the absolute target path with a `rem open-second-brain launcher ->` ownership marker (`install-cli-windows.ts:14-48`).

Places that would have to produce "absolute Bun + launcher inside the installed package": `payload.ts` `launcherCommand`/`COMMAND` (4), `grok-asset.ts` `bunBin`/`MAIN_TS`/`hookCommand` (3), `install-cli.ts` `CLI_SCRIPTS`/`findScript` (5), `install-cli-windows.ts` `launcherBody` (6), `pi.ts` `resolveSourcePath` (symlink source), `opencode-plugin-asset.ts` `PLUGIN_SOURCE_PATH`, and the `--check`/verify twins `payload-equals.ts:12-19` and `command-probe.ts` (the probe's grok `bun run <path>` interpretation, `command-probe.ts:33-34`).

## 3. How the code knows where it is installed from

There is **no install-origin record at all**. Everything is positional:

- `import.meta.url/dir` walks: `install-cli.ts:30-33` (repo root two levels up), `pi.ts:53-55`, `aider-wrapper.ts:40`, `grok-asset.ts:29`, `opencode-plugin-asset.ts:17-21`. Under a registry install these resolve to `<global pkg dir>/…`, which is actually the desired root — but nothing distinguishes it from a clone, and the `hooks/` directory they reference **is not shipped** (`package.json "files"` `package.json:32-44` lists `bin/, openclaw/, src/, skills/, scripts/, plugins/, schemas/…` — no `hooks/`), so grok's hook commands and `o2b-hook`'s `hooks/<name>.ts` probe would fail to find sources.
- Env overrides: `OSB_PLUGIN_ROOT` (`pi.ts:59`, `scripts/o2b-hook:51-56`), `CLAUDE_PLUGIN_ROOT` (`hooks/hooks.json:9`, `scripts/o2b-hook:38-43`), `CODEX_HOME`/`GROK_HOME`/`PI_HOME`/`XDG_CONFIG_HOME` (`codex.ts:181`, `grok.ts:54-56`, `pi.ts:68-70`, `opencode.ts:87-91`).
- Launcher-side resolution: `scripts/o2b:7-9` and `scripts/o2b-mcp:7-9` compute `REPO_ROOT` from `realpath $BASH_SOURCE` — a bun/npm bin shim symlink resolves fine — and `scripts/_bun-precheck.sh:80-101` then checks `node_modules/proper-lockfile` and runs `bun install --frozen-lockfile` **inside that root** if missing (a registry install ships a populated `node_modules` only if not pruned; bun's global installs do keep dependencies, npm's global layout keeps them hoisted, so this is mostly a no-op — but it is written in "checkout" vocabulary).
- `underPluginCache()` `install-cli.ts:102-106` keys on the literal substring `plugins/cache` — the only "where did this come from" heuristic in the tree, and it knows exactly one provider.
- A registry install under `<pm-global>/node_modules/open-second-brain` would **not** be misdetected as a clone (nothing tests for "clone"), but every consumer above treats it as "whatever checkout the launcher lives in", which is indistinguishable and unverifiable; the marketplace-cache special case is Claude-only.

## 6. What `doctor` / `install --check` report today, and the registry gap

Today:

- `install --check` per target: adapter `verify()` — manifest presence, config-byte comparison against `expectedPayloadFromEnv` (`src/core/install/payload-equals.ts:12-19`), and for codex/copilot a host probe (`probeHost` `src/core/install/host-probe.ts:293-326`: `codex mcp list` / `copilot mcp list`, first-column name matching `:247-262`); verdicts `ok / drift / not-installed / mcp-unreachable` (`types.ts:39-45`); detail lines name the config path and the probe note (`handshakeNote` `host-probe.ts:332-345`); exit 3/5 ranking `src/cli/install/install.ts:692-696`.
- `o2b doctor --readiness` probes (`src/core/doctor-readiness.ts`): `probeInstalledRuntimes` (each installed adapter's `verify`), `probeRuntimeAdapterWiring` (payload constructible), `registered_commands` (t_3477c9e8, `:1042-1116`: re-reads the manifest's `config_path`, extracts the registered OSB command, and grades resolvability via `probeCommandResolvability` `src/core/install/command-probe.ts:118` — verdicts `resolves / absent / unresolved`, with a grok `bun run <path>` file leg `:33-34` and a `fix: o2b install <target> --apply` recovery line `:1103-1106`), `client_versions` (`:1126-1143` per-client `--version` table, runner `:1160-1240`), `writeback_contract` (`:127-131`), plus provider/credential probes. Base `doctor()` (`src/core/doctor.ts:35-291`) checks vault/config writability and plugin-manifest shapes.

For a registry install they would additionally need to report (all currently absent): **which executable the registered command actually is** (the payload's bare `o2b` says nothing about which prefix supplied it); **whether another provider shadows `o2b` on PATH** (`command-probe.ts` deliberately returns a single resolution and its `unresolved` verdict explicitly refuses to claim "broken", `command-probe.ts:16-20` — there is no shadowing check anywhere); **registered version vs running version** (`client_versions` asks the *client's* version, never OSB's own — no probe compares `OPEN_SECOND_BRAIN_VERSION` `src/core/version.ts` with what a spawned `o2b --version` answers); **stale paths** (only the Claude plugin-cache symlink healer `install-cli.ts:204-235` knows the concept); **duplicate hooks** (nothing deduplicates `[mcp_servers.*]` entries beyond codex's own `remove`-then-`add` `codex.ts:281`, and no probe counts multiple OSB registrations).

## 9. Risks and open questions (priority order)

1. **`hooks/` is not shipped in a registry install.** `package.json "files"` (`package.json:32-44`) omits `hooks/`, yet grok's installer registers `bun run <REPO_ROOT>/hooks/<name>.ts` (`grok-asset.ts:65-67`) and `o2b-hook` only runs when it finds `hooks/<name>.ts` (`scripts/o2b-hook:33-56`). Either the hook sources ship compiled/elsewhere, or `setup` cannot register hooks at all from a registry install (§3).
2. **The registered command vocabulary has exactly two shapes today — bare `o2b` and clone-absolute `bun run <repo>/…`** (`payload.ts:26,53`; `grok-asset.ts:54-55`) — and `verify` reconstructs the expected bytes from `InstallEnv` alone (`payload-equals.ts:12-19`). A third shape ("absolute bun + launcher in the installed package") must be derivable from `InstallEnv` at verify time or every fresh install reports drift against itself (§2, §6).
3. **Origin detection does not exist**, so `setup` cannot distinguish "installed from a registry at prefix P, version X" from a clone/marketplace cache; the only positional heuristic is the literal `plugins/cache` substring (`install-cli.ts:102-106`). A manifest extension (§5) has no producer to trust and no reader (§3, §5).
4. **No shadowing/duplicate detection.** `command-probe.ts:16-20` refuses to claim "broken" for an unresolvable bare name and stops at the first PATH hit (`:215-241`); nothing reports a second provider's `o2b` earlier on PATH or a duplicated OSB registration — exactly the failure modes a one-shot setup must catch (§6).
5. **The consent gate forces a design decision.** `install --target X --apply` refuses without `--yes` when non-interactive (`src/cli/install/install.ts:509-528`, exit 6) and asks on a TTY; a headless `setup` must either compose `--yes` internally (as the interactive wizard already does, `init-interactive.ts:275-284`) or inherit the gate (§1).
6. **`o2b-hook` is not a registry bin.** `package.json bin` (`package.json:26-30`) ships `o2b`, `o2b-mcp`, `vault-log` only; `o2b-hook` reaches PATH solely via `install-cli` (`src/cli/install-cli.ts:28`), and `hooks/hooks.json:9`'s fallback chain assumes either `CLAUDE_PLUGIN_ROOT` or a PATH `o2b-hook`. `setup` must decide what "registered hooks" even means for non-plugin hosts (§2, §3).
7. **The launcher itself is bash + realpath-dependent.** `scripts/o2b:7-9` resolves `REPO_ROOT` via `realpath $BASH_SOURCE`, and `_bun-precheck.sh:80-101` may run `bun install --frozen-lockfile` *inside the installed package*; a pm-managed prefix (read-only or content-addressed stores) can break both, and `bin/*.js` launchers mentioned for the registry install are a different entry shape than today's `scripts/*` bash wrappers (`package.json:26-30` vs `bin/o2b-discipline-report`) (§3).
8. **Which hosts `setup` configures vs instructs is already encoded twice, not once** — bootstrap's `BOOTSTRAP_TARGETS` mode table (`src/cli/bootstrap/targets.ts:36-43`) vs the adapter registry (`adapters/all.ts:15-24`) vs the closed target vocabulary (`host-facts.ts:61-88`) — with `claude-code`/`zcode` existing only in the first. A `setup` verb must pick one source of truth or re-create the desynchronization the census test guards against (`types.ts:176-178`) (§4).
